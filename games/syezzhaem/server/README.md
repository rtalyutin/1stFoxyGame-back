# API и данные R1

Better Auth 1.7.7 обслуживает /api/syezzhaem/auth/: email/пароль, обязательное подтверждение адреса, восстановление и PostgreSQL-сессии. Cookie: prefix syezzhaem, HttpOnly, SameSite=Lax, отдельный API path и Secure на HTTPS. Origin ограничен конфигурацией. Пароли обрабатывает библиотека; игровые таблицы их не содержат.

Игровой RPC: POST /api/syezzhaem/v1/rpc/<operation>, JSON и X-Syezzhaem-Expected-User, совпадающий с проверенной сессией. Заголовок защищает от смены аккаунта между проверкой и отправкой; авторизацию определяет серверная сессия. Ответ {ok,data,error,request_id}. Снимок — src/snapshot-v1.ts, DTO — src/r1-contracts.ts.

| Операция | Вход |
|---|---|
| bootstrap_v1 | client_build |
| profile_update_v1 | expected_revision, settings, request_id |
| run_start_v1 | client_build_id, level_id, content_version, request_id |
| run_get_v1 | run_id |
| checkpoint_save_v1 | run_id, expected_revision, snapshot, request_id |
| run_finish_v1 | run_id, expected_revision, snapshot, outcome, request_id |
| run_abandon_v1 | run_id, expected_revision, request_id |
| history_list_v1 | cursor, page_size (1–30) |

Запись: одна транзакция, блокировка профиля/корня, успешная дедупликация, CAS, полная валидация, EAV/проекции и ACK. Отказ не резервирует ключ. Повтор успешной команды возвращает прежний ответ до проверки текущей revision/активного слота. Один активный run на аккаунт. Итог выводится из снимка и исходных ID; проигрыш даёт ноль. Клиентская симуляция не доказывает честность прохождения; публичного рейтинга нет.

EAV: реестры типов/параметров, сущности, шесть типизированных колонок значений. Составные FK, deferred required и триггеры ограничивают типы, диапазоны, родителя и владельца. Базовая карта не дублируется: сохраняются tombstone/новые клетки, игрок/дом и инвентарь. JSONB допускается только в техническом сохранённом ACK идемпотентности.

Приватные таблицы защищены RLS. set_config(..., true) задаёт owner из сессии внутри транзакции, после commit/rollback контекст не остаётся в пуле. Runtime не владеет таблицами и не наследует повышенные роли. Группы и DDL — db/000-roles.sql, 001-r1.sql, 002-auth.sql; метаданные — server/r1-metadata.ts. Установку выполняет отдельный мигратор.

/api/syezzhaem/v1/version сообщает контракт/build API, ready проверяет Auth/DB/каталог. Operator drain требует loopback и отдельный секрет, nginx его не публикует. Лимит тела 512 KiB, два новых checkpoint/с на пользователя; retry принятой команды и контролируемый финиш не создают второго эффекта. Логи содержат request_id/операцию/код/время без снимков, паролей, cookie и почтовых ссылок.

Better Auth ограничивает `/get-session` отдельным правилом 600 запросов/мин: проверка аккаунта до и после сохранения при допустимых двух checkpoint/с требует 240 чтений/мин, дополнительно нужны меню и продолжение. Вход остаётся ограничен 10 запросами/мин, регистрация и восстановление — 5 запросами/мин. Это действующая конфигурация сервера, без обхода Auth в тестах.

Секреты, база и письма не входят в архив. Срок хранения, RPO/RTO и production backup-политика требуют выбора перед публичным выпуском. Выполненные проверки и ограничения — evidence/qa-report.md.

### Типизированная БД и восстановление

Игровые данные R1: `server/r1-store.ts`, `server/r1-metadata.ts`, `db/001-r1.sql`. Прогресс разбирается в EAV-профиль, забег, checkpoint, игрока, дом, инвентарь и overrides неизменяемой карты. Типы, обязательность, диапазоны и настоящие ссылки проверяются SQL; `request_dedup.response` служит только журналом успешных ACK. Восстановимые индексы профиля, активного забега и ключей не являются второй копией прогресса.

`MIGRATION_DATABASE_URL=… node --import tsx server/migrate.ts` — отдельный операторский запуск. Он блокирует миграционный ключ, применяет additive game/Auth DDL и проверяет неизменяемый контент в одной транзакции. Уже существующие схемы без известного `schema_migrations` отвергаются. Runtime API не создаёт таблицы и не меняет каталог. LOGIN-роли и пароли создаются оператором вне репозитория; игровые и Auth credentials не должны наследовать миграционную роль.

`server/r1-recovery.ts` экспортирует канонические игровые EAV-таблицы и ACK-журнал, восстанавливает их в отдельную пустую мигрированную схему и собирает технические индексы заново. Он не включает Auth-секреты и аккаунты: для полного восстановления установки нужен защищённый резервный экспорт PostgreSQL вместе с `syezzhaem_auth`, неизменяемыми каталогами сборок и операторскими секретами. Restore выполняется сначала в отдельную тестовую БД. Обратная несовместимая миграция не удаляет новые данные ради rollback.

`tests/data.test.ts` выполняет реальные PostgreSQL проверки двух пулов, CAS, активного слота, ACK retry, полного отказа снимка, типов/required/ссылок, расширения метаданных, версии контента, результата и export/restore. В контейнере с единственным UID0 тестовый PostgreSQL запускается только с явно выбранным QA shim `tests/data-pg-uid-shim.c`; SQL-движок, роли и RLS остаются штатными. Этот способ не подтверждает настройки ОС/Unix socket целевого VPS.
