# Last Throne database: R3 with retained R1/R2

The schema `last_throne` belongs only to this game. Migrations do not inspect or modify the first game's tables. The retained R0 migrations create typed EAV metadata/content foundations. R1 adds guest sessions, owner-authorized profiles/runs, immutable checkpoint generations and idempotent terminal results. R2 adds revised magic state; R3 adds typed item slots, expeditions, pending rewards and hero-bound Aegis. Published migrations001–006 and exact R1/R2 data/handlers remain unchanged.

Run `DATABASE_URL=... node scripts/migrate.mjs` with the migration owner. The URL must identify the dedicated Last Throne database/role. Each SQL file is applied in one transaction, and its SHA-256 is recorded in `last_throne.schema_migrations`. Repeated execution skips exact matches; modified history fails. A non-blocking session advisory lock prevents simultaneous migrators: contention fails with `MIGRATION_BUSY`. Lock waits are bounded to 5 seconds and statements to 60 seconds. Recovery after a failed migration is another invocation of this command. There are no destructive `down` migrations.

`001_typed_eav.sql` creates metadata, entities, typed values, publication functions and the content catalog. Composite foreign keys pin every value to the entity's exact type and parameter data type. A value occupies exactly one typed column. A single value must have ordinal zero; multiple values have unique non-negative ordinals. Drafts may omit required values, but publication/freeze rejects omissions. The bounded constraint language accepts numeric `min`/`max`, text `minLength`/`maxLength`, and scalar `enum`; executable expressions are rejected.

Published metadata, entities, values and content releases are immutable. Adding a parameter after publication requires a new type revision with new parameter IDs and a new metadata schema. References pin the target type and declare `same_owner`, `same_run`, `same_checkpoint` or `pinned_release`. Referenced targets cannot be deleted or have their scope changed. A deferred constraint rejects finalized entities that reference editable draft targets, while allowing a complete group to finalize in one transaction. Existing published versions are retained. Runtime reads use `db/content.mjs`, which derives the JSON response from EAV truth and preserves explicit zero/false values. Multiple parameters return ordered `{ordinal,value}` entries, preserving gaps in the stored ordinals. Metadata and content seed hashes are SHA-256 of the corresponding `canonicalJson` projections, and tests verify them against the live EAV rows.

The coarse transaction advisory lock introduced in R0 still serializes metadata/entity/value changes, publication and R1 persistence writes. R1 authorizes each run operation and implements revision/idempotency checks under that lock. Lock and statement timeouts bound work; concurrent save throughput remains a capacity limit to measure on the target PostgreSQL server.

The seed `002_r0_catalog.sql` publishes `r0-meta-1` and `r0-content-1`, with only technical application settings and `gameplay_available=false`. It does not create heroes, towers, battle state or Dota assets. Publication switches the technical catalog channel atomically. Switching the browser launcher to content that needs new behavior remains the deployment operator's responsibility and must use a new launch release ID.

## Database roles

Use distinct credentials. The migration owner owns the schema. The API must be a separate non-owner role without membership in that owner role or superuser privileges. After the current migration, apply `db/r3-runtime-grants.sql` as the dedicated schema owner for the `last_throne_api` role provisioned by the runbook. That file replaces historical blanket reads with an explicit content/EAV read allowlist and named, bounded R1/R2/R3 function grants. Old versioned grant files remain for their retained artifacts.

Functions and tables have no PUBLIC privileges. The API has no direct table writes or metadata/content publication privileges. `ALTER DEFAULT PRIVILEGES` must be run by the migration owner. Do not reuse the first game's database credentials. The infrastructure runbook provisions roles; the additive migrations do not require cluster-level `CREATE ROLE` privileges.

## Local verification

Current R3 storage/API acceptance runs with `node --test tests/database-r3-storage.test.mjs tests/server-r3-http.test.mjs`. See `docs/DB-R3.md` for exact hashes, typed decomposition, migration/grant commands and the same storage assertions against an optional fresh dedicated PostgreSQL17 `td_db`. R3 projections are checked against stored canonical SHA before serving content or ETag. SQL007/008 publication guards validate known handlers even under future metadata revisions.

`node --test tests/database.test.mjs tests/r1-database.test.mjs tests/r1-api.test.mjs` runs PostgreSQL SQL in PGlite and the R1 HTTP contract in Fastify. Tests execute the real constraints/functions and migrations, including transaction failure, immutable metadata movement, value types, reference boundaries, atomic publication and the persistence scenarios below. PGlite is a local PostgreSQL engine; it does not prove the production server's capacity, backup/restore, network configuration or behavior of multiple independent PostgreSQL sessions. Real-server migration/readback checks are required before activation.

## R1 persistence

`003_r1_persistence.sql` adds typed-EAV profile, run, checkpoint, saved hero/building and result definitions. It stages the new `r1-meta-1` membership as draft. Only three additional tables are technical: `guest_sessions` stores a SHA-256 token hash and expiry; `run_client_keys` enforces `(owner,clientRunId)` creation idempotency; `save_operations` retains `(owner,run,requestId)`, canonical request hash and committed response. Game values are not stored as a JSON snapshot. Four deterministic statistics counters are individual integer parameters on checkpoint/result. Snapshot reconstruction derives the complete JSON from scalar values and immutable references.

`004_r1_catalog.sql` completes content type/parameter metadata, publishes the whole metadata schema, publishes the immutable R1 EAV catalog and switches its catalog channel. Stable IDs and canonical metadata/content hashes are generated by `node db/build-r1-seed.mjs` from the controlled `core/content-r1.ts` descriptors. This is a developer build command and requires PGlite; the delivered SQL migration has no PGlite runtime dependency. Regeneration is allowed only before that migration is published/applied. Future changes require a new metadata/content release and a new migration, never editing published history. Ordinary `node scripts/migrate.mjs` is sufficient at deployment; there is no gameplay seed on API startup.

The API calls `createGameStore(pool)` from `db/game-store.mjs`. Writing uses bounded `SECURITY DEFINER` functions with a fixed `pg_catalog,last_throne` search path and PUBLIC privileges revoked. Apply `db/r1-runtime-grants.sql` as the dedicated schema owner to replace R0 blanket reads with a content table allowlist and grant the API role these operations. Direct reads of guest sessions, operation journals, run creation keys and migration history are revoked. Future table read grants and PostgreSQL's global PUBLIC function EXECUTE default are revoked for this owner; a schema-local REVOKE cannot remove that global built-in default. The owner must belong only to Last Throne. The generic EAV helpers, configuration publication functions and direct table writes remain unavailable to that role. The HTTP layer resolves the session owner; no client-supplied owner ID is accepted. This is a trusted backend boundary, not protection against a malicious holder of backend credentials.

Checkpoint commits retain one connection and one transaction. They acquire the existing coarse EAV advisory lock before the run row lock, authorize the owner and check the shared request journal before terminal state/revision. An exact historic repeat returns its recorded response even after finish. The lazy validator receives `(run,client)` after those checks and must read pinned content using that same client; a pool query inside the callback can deadlock when the pool has one connection. Full typed generation and links freeze together under the deferred reference closure, followed by run pointer/revision and operation insertion. Failure rolls the generation back. Finish uses the same order, writes one typed result, freezes the terminal run and persists the response in one transaction; it does not require a checkpoint. GET checkpoint reports the generation's committed revision from its accepted operation and separately `runRevision`, so finish does not relabel an older snapshot. Finish checks the pinned catalog's throne HP limit and final wave, including the victory/defeat wave relationship. Every result stores the required typed boolean `client_reported=true` (metadata enum permits only true). Results are client-reported and are not anti-cheat attestations.

The coarse R0 advisory lock deliberately remains and serializes writes across this game's players. Statement/lock timeouts bound wait/work; it is a documented capacity limit requiring measurement on PostgreSQL before scaling. R1 tests exercise actual SQL in PGlite: additive R0 preservation, catalog/hash readback, profile settings, owner isolation, creation/revision/request conflicts, complete typed checkpoint roundtrip, immutable closure, partial-write rollback, finish uniqueness and post-finish historic repeats, and actual non-owner role permissions. PGlite uses one SQL session, so these tests do not claim independent-session race/capacity validation on the shared production VPS.
