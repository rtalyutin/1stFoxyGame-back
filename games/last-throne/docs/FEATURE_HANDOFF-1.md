# FEATURE_HANDOFF/1


Применять при передаче между этапами и приёмке; профиль навыка определяет предметные критерии. Для простого самостоятельного задания достаточно релевантной части, без пустых полей и нового проектного протокола.

| Поле | Семантика |
| --- | --- |
| `feature_id` | Устойчивый идентификатор фичи в существующей системе учёта. При её отсутствии — идентификатор текущей карточки; не выдумывать ID внешней системы |
| `contract_revision` | Версия цели, объёма, критериев и полномочий; связь с подтверждением пользователя |
| `artifact_revision` | Проверяемая версия результата: commit и состояние рабочей копии, digest сборки либо версия документа. Одного имени файла недостаточно |
| `producer`, `consumer` | Кто подготовил и кто принимает. Реальные исполнители отдельно от названий навыков |
| `inputs` | Ссылки на использованные входы и их версии; позволяет определить последствия поправки |
| `scope` | Что именно покрывает результат и какие части не проверялись |
| `evidence_status` | `PREPARED`, `EXECUTED`, `VERIFIED` или `STALE`, в значениях ниже |
| `gate_verdict` | `PASS`, `FAIL`, `BLOCKED` или `NOT_APPLICABLE`; оценивает только названную границу и её критерии |
| `evidence` | Для каждого существенного вывода: источник/лог/расчёт/наблюдение, версия, среда, время получения и ограничения |
| `exceptions` | Остаточные дефекты, принятый риск, кто и в каких границах его принял; отсутствие разрешения не считать исключением |
| `next_action`, `return_to` | Следующее действие либо конкретная причина возврата и принимающий исправление |
| `authorization_ref` | Основание для внешней операции: действие, цель, среда, аудитория и границы. Старое разрешение сохраняется в своём объёме |

`PREPARED`: результат подготовлен. `EXECUTED`: действие или проверка фактически выполнены. `VERIFIED`: конкретный результат проверен по названным критериям. `STALE`: изменилось использованное основание; старые доказательства сохраняются, но не подтверждают новую версию. Проверенное ТЗ не означает выполненную реализацию.

`PASS`: выполнены критерии конкретного gate. `FAIL`: наблюдаемое нарушение. `BLOCKED`: не хватает входа, доступа, разрешения или достоверного наблюдения. `NOT_APPLICABLE`: проверка неприменима с указанным основанием; использовать для обхода обязательного критерия запрещено.

Отдельно от `gate_verdict` хранить два поля:

- `action_decision`: `CONTINUE`, `ITERATE`, `STOP`, `UNDECIDED` — практическое решение по следующему вложению/действию. `UNDECIDED` означает, что решение пока не принято, и не разрешает продолжение расходов.
- `hypothesis_assessment`: `SUPPORTED`, `REFUTED`, `INCONCLUSIVE`, `NOT_ASSESSED` — вывод о конкретной версии гипотезы по установленному методу. Первые два значения требуют различающего evidence; `INCONCLUSIVE` означает недостаточный или неоднозначный результат, `NOT_ASSESSED` — эмпирическая проверка ещё не проводилась. Статусы не расширяют силу метода: корреляция не подтверждает причинное утверждение.

Корректный аналитический отчёт может пройти приёмку с `action_decision=STOP` и `hypothesis_assessment=INCONCLUSIVE`, например когда закончился разрешённый бюджет. При недостатке данных и отсутствии установленного правила действия — `UNDECIDED` и `INCONCLUSIVE`. Для подготовки нового теста возможен `NOT_ASSESSED`; решение инвестировать не является подтверждением гипотезы. Техническое качество, полнота исследования и положительная полезность — разные выводы.

Для внешней операции хранить `operation_status`: `NOT_STARTED`, `IN_PROGRESS`, `SUCCEEDED`, `FAILED`, `UNKNOWN`, а также полученный от среды идентификатор, если он есть. Таймаут даёт `UNKNOWN`, пока исход не установлен. Повтор возможен после сверки состояния и проверки безопасности повтора; новое имя или новая версия не используются для маскировки дубликата.

## Версия и поставка

Владелец определения — run-roman-control-loop. Этот файл является эталоном в Контуре и идентичным локальным снимком в профильных навыках. При передаче указывать handoff_schema=FEATURE_HANDOFF/1 и handoff_digest=SHA-256 байтов этого файла (например, sha256sum references/feature-handoff-contract.md). Digest не включать в хешируемый файл.

Сравнивать schema и digest у отправителя и получателя. При несовпадении выяснить различия; не интерпретировать молча. Изменение семантики требует новой версии, проверки потребителей и явного преобразования при совместимости. Отсутствие другого установленного навыка не блокирует локальную работу по собственному снимку. Не создавать независимые варианты одной версии.

Один ACTIVE_CONTRACT и TASK_STATE принадлежат координатору; профиль возвращает результат. Для прямого вызова достаточно относящихся к задаче полей без запуска всего конвейера. Неизвестное блокирует только зависимое действие. Пороги и лимиты брать из действующего контракта, не придумывать универсальные значения. Согласие исполнителей не заменяет наблюдение. Принятый риск не подменяет разрешение или обязательный gate. Реальные агенты, доступные инструменты и фоновые службы проверяются отдельно от наличия навыка.
