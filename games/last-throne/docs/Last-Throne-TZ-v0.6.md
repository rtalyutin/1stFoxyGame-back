# «Последний трон» — техническое задание

Версия: 0.6, 7 октября 2026. Проект: FoxyGames. Дополнение: реализация R3 — полная партия; целевое размещение на сервере первой игры.

**Статус: R0/R1/R2 проверены; R3 реализуется по поручению пользователя, итоговый gate ещё не закрыт; R4 остаётся проектом.** R2 включает десять волн, пять героев, три семейства зданий и кражу/применение магии. Старый R1 остаётся отдельной пятиволновой партией. Точный состав и основания проверок — §10.1 и §10.3. Установка на целевой VPS не выполнена. Баланс требует пользовательского плейтеста, производительность — измерений на целевой технике.

## 0. Назначение, основания и границы

Самостоятельная браузерная tower defence в мире Доты. Игрок защищает последний трон на компактной карте с тремя линиями, размещает сооружения, усиливает героев и вручную применяет способности. Характерный опыт: спасти почти проигранную оборону комбинацией позиционирования, заклинаний и переброски героев.

### 0.2. Открытые решения

Для реализации R1/R2 и продолжения R3 по U11 применяется базовый вариант из §8.1: **одиночная игра на ПК, гостевой профиль без регистрации, локальный бой и облачные контрольные сохранения**. Это рабочая граница трёх игровых поставок; U09–U11 не подтверждают предпочтения для мобильной версии, авторизации или R4.

| Решение | Предложение | Что зависит от согласования |
|---|---|---|
| O01: устройства | Сначала ПК, мышь/клавиатура | Матрица приёмки; мобильный HUD и сенсорные жесты остаются отдельным объёмом |
| O02: идентификация | Гость в одном браузере | Вход, восстановление доступа и перенос между устройствами не входят в описанный базовый вариант |
| O03: содержание поставок | Поэтапно R1–R4 из §8.1; полный базовый игровой набор достигается в R3 | Предлагаемые размеры ранних релизов и критерии их приёмки |
| O04: баланс | Стартовые настройки и конкретные правила из §2 | Их можно реализовать после принятия; удовольствие и сложность требуют плейтеста |
| O05: контрольная техника | Выбрать фактический ПК и браузеры до графической приёмки | Нельзя подтвердить FPS и загрузку без эталонного оборудования |
| O06: использование мира Dota при распространении | Проверить применимые права до публичного выпуска | Названия, персонажи, заимствованные материалы; смена мира без решения пользователя не допускается |

U09 разрешает реализацию ограниченного R1; U10 продолжает её ближайшим R2 по §8.1 с теми же базовыми решениями. Будущие изменения устройства, идентификации, размера поставок и баланса фиксируются отдельно; O05/O06 остаются условиями соответствующей последующей приёмки.

## 1. Готовые инструменты и предлагаемая архитектура

### 1.1. Рекомендация

**Babylon.js + TypeScript + Vite для игры; HTML/CSS для HUD; Node.js + Fastify для одного API; PostgreSQL для конфигурации и сохранений.** Модели — Blender → GLB. Материалы и частицы — готовые редакторы Babylon.js. Окружение и базовые текстуры эффектов — подходящие наборы Kenney/KayKit с проверкой лицензии каждого используемого файла.

Это архитектурная рекомендация, а не результат нагрузочного сравнения движков. Основание: требуются браузерный 3D-рендер, контроль над игровым кодом, импорт моделей, насыщенные эффекты и независимый обычный веб-интерфейс. Эти возможности присутствуют в документации Babylon.js [S01–S03].

Не нужен собственный редактор частиц, собственный формат 3D-моделей, физический движок для крюка или отдельный сервис на каждый модуль. Для карты первой версии достаточно сцены в Blender и проверяемого описания путей/площадок; пользовательский редактор карт не входит в базовый объём.

**Что готовые наборы не закрывают:** точные модели героев Dota, их узнаваемые движения, законченные комбинации способностей, баланс волн и авторский рисунок магии. Эти части не помечаются как «найдены готовыми».

### 1.3. Альтернативы

| Вариант | Когда полезен | Цена выбора для этой игры | Решение |
|---|---|---|---|
| Babylon.js + код и специализированные редакторы | Основная работа через TypeScript, независимый хостинг, обычный веб-HUD | Сценарии боя и сборку карты нужно организовать самостоятельно | Рекомендуемый базовый вариант |
| PlayCanvas Editor + Engine | Приоритет визуальной сборки сцен в браузере | Новый рабочий процесс, проект в редакторе, проверка доступа/тарифа и экспорта | Сильная альтернатива; сравнить на одной сцене, если визуальная сборка станет узким местом |
| Godot → Web | Нужен единый редактор сцен и анимаций с перспективой других платформ | Для web действуют ограничения экспорта; отдельная интеграция с HTML-интерфейсом | Возможен, но не основной вариант для этого ТЗ |

PlayCanvas документирует редактор, сценовую сборку, скрипты и самостоятельный хостинг [S11]. У него также есть **официальный Editor MCP Server**: он работает с уже открытой сессией редактора, позволяет менять проект и проверять viewport/запущенное приложение [S12]. Это реальный кандидат на автоматизацию сцены ассистентом, но он сейчас не подключён; наличие документации не означает наличие доступа.

Godot поддерживает web-экспорт; в проверенной документации указаны WebAssembly/WebGL 2, Compatibility renderer и ограничения C#-экспорта. Однопоточный вариант поддерживается, поэтому многопоточность и специальные заголовки нельзя объявлять обязательными для любого Godot web-проекта [S13].

**Фактическое использование в R1/R2:** Babylon.js 9.29.0 установлен через npm и проверен в настоящем WebGL2; сцена, модели и эффекты построены процедурно в коде. Blender/PlayCanvas, импортированные GLB и наборы Kenney/KayKit в поставки R1/R2 не включены. Imagegen пригоден для концептов и растровых элементов, но не выдаёт готовый ригованный GLB. Вместо ранее предложенного Vitest используются встроенный Node test runner и Playwright; версии закреплены в lockfile.

### 1.4. Границы компонентов

| Компонент | Владеет | Не делает |
|---|---|---|
| `game-core` | Симуляция, правила, команды, золото, HP, кулдауны, волны, состояние вылазок | Не обращается к DOM, Babylon, БД или сети |
| `game-renderer` | Модели, эффекты, камера, звук, отображение событий ядра | Не решает, нанесён ли урон и хватает ли золота |
| `game-ui` | HUD, меню строительства, подсказки, команды игрока | Не изменяет состояние боя обходным путём |
| `api` | Профиль, сохранение контрольных точек, версии контента, доступ к данным | Не считает каждое движение крипа и каждый кадр |
| `content-publisher` | Проверка и выпуск неизменяемого набора данных/ассетов | Не заменяет правила игры произвольным исполняемым кодом из БД |
| PostgreSQL | Метаданные, версии контента, профиль и сохранённые сущности | Не участвует в покадровой симуляции |

В бою источник текущего состояния — `game-core` в браузере. Сервер является источником опубликованного контента и сохранённых контрольных точек. **Сохранённый клиентский результат не считается доказанным честным рекордом.** Публичный рейтинг, призы и соревновательная защита потребуют отдельной серверной проверки и не входят в базовый вариант.

## 2. Общие игровые правила и контракт симуляции

В этом разделе описан полный базовый вариант для R3. R1 реализует применимые правила только для своего состава из §8.1; точные опубликованные значения первой поставки приведены в §10.1. Изменения отражаются одновременно в ядре, интерфейсе, конфигурации, графике и тестах.

### 2.1. Состав полной базовой партии, достигаемый в R3

- Одна компактная карта, три основных маршрута к трону и заранее заданный боковой путь диверсантов.
- Пять героев: Pudge, Undying, Rubick, Shadow Shaman, Sniper.
- Три семейства постоянных сооружений: баллиста, магическая башня, тотем замедления. У каждого — три уровня, включая исходный.
- Шесть обычных ролей противников: ближний боец, стрелок, лекарь, осадная машина, диверсант, бронированный элитный боец.
- Три волны с командирами: предлагаемые номера 5, 10 и 15. Роли: осада, обход, магическое усиление. Конкретные образы командиров выбираются при графической спецификации контента.
- Предлагаемые 15 волн и целевая длительность 15–20 минут. Длительность — цель балансировки, а не гарантированное свойство документа.
- Вылазки: нейтральный лагерь, тайная лавка, Рошан; одно одновременное отсутствие героя в предлагаемом базовом варианте.
- Победа: последняя волна полностью завершена, трон жив. Поражение: HP трона достигло нуля. При обоих событиях на одном такте приоритет у поражения.

### 2.2. Размещение, деньги и разрушение

**RULE-01.** Постоянные здания занимают только участки `building_pad`. Герои занимают отдельные `hero_anchor`. Один тип места нельзя использовать вместо другого. Призывы создаются в разрешённой области способности, не занимая строительный участок.

**RULE-02.** Полностью блокировать дорогу постройками нельзя. Размещение не меняет граф путей. Пустая/занятая/выбранная площадка различаются формой, контуром и значком; различие не зависит только от цвета.

**RULE-03.** Строительство возможно в подготовке и бою. Команда проверяет тип и доступность места, стоимость, фазу партии и отсутствие другой операции. При принятии атомарно списывает золото и резервирует участок. В бою здание активируется после указанного в конфигурации числа тактов; в подготовке — сразу в игровом состоянии, с косметической анимацией сборки. Окончание волны завершает оставшуюся стройку по §2.5. Задержка визуальной анимации не создаёт дополнительного списания и не блокирует сохранение.

**RULE-04.** Улучшение атомарно списывает стоимость и переводит объект на следующий уровень. Продажа предлагается только в подготовке; стартовый возврат — 70% суммарно потраченного золота с округлением вниз. Разрушение врагом даёт 0 возврата. После разрушения участок освобождается, а обломки остаются только визуальными.

**RULE-05.** Золото — целое неотрицательное число, принадлежит текущей партии. За одного погибшего врага награда выдаётся один раз независимо от числа источников урона. Между партиями золото и купленные боевые улучшения не переносятся. Профиль хранит настройки и историю; постоянная метапрокачка не предполагается.

**RULE-06.** У каждого героя есть уровни улучшения за золото и два предлагаемых слота предметов. В первой версии предметы используют готовые обработчики: дополнительная цель, ускорение перезарядки, обнаружение скрытых врагов, лечебная аура. Совместимость и пределы модификаторов задаются конфигурацией. Покупка недопустимого/дублирующего уникальный эффект предмета отклоняется до списания.

| Pudge | Ближняя атака в зоне позиции | Крюк выбирает одну видимую допустимую цель. Босс может иметь запрет перемещения. При исчезнувшей до принятия цели нет расхода; после старта каст завершается по правилу способности | Цепь натягивается, противник физически переносится к точке притяжения |
| Undying | Атака и поддержка своей зоны | Призыв временного надгробия в допустимой области; зомби создаются с заданными лимитом и временем жизни | Круг, трещины, руки и последовательное появление зомби |
| Rubick | Магическая атака | Первый каст крадёт последнее помеченное `stealable` заклинание выбранного командира; следующий расходует сохранённое заклинание. Кража и применение имеют отдельные кулдауны | Фрагменты чужого эффекта втягиваются в посох; сохранённое заклинание видно на кнопке |
| Shadow Shaman | Дальняя атака | Временные змеи в выбранной разрешённой области. Не закрывают навигационный проход; число и TTL ограничены | Рунический круг и последовательный подъём змей, затем согласованный залп |
| Sniper | Дальняя атака с выбранным приоритетом | Прицельный выстрел по одной допустимой цели после подготовки. Ограничения видимости/дальности проверяются при старте; правило потери цели задано явно | Линия прицеливания, короткий импульс и попадание |

Для базового набора украденных способностей Rubick предусмотреть три известных обработчика: лечение в области, удар в область, временный щит. Новый неизвестный `behavior_id` должен блокировать публикацию набора контента. Универсальное исполнение произвольного кода из БД запрещено.

Цель, умершая после старта снаряда/подготовки, не получает повторный урон; начатая способность тратит кулдаун. Визуал показывает исчезновение цели или завершение без попадания. Это предложенное общее правило, исключение возможно только в явной конфигурации обработчика.

**RULE-07.** Между волнами перестановка героя бесплатна. Во время волны телепортация расходует свиток, купленный за золото, и длится заданное число тактов. Свиток расходуется один раз при принятии команды; назначение резервируется. До завершения герой остаётся на исходной позиции и не атакует. Гибель прерывает перенос, освобождает резерв и не возвращает свиток. Отмена игроком возможна до принятия команды, затем — нет.

**RULE-08.** Герой может погибнуть. Предлагаемое время возвращения — 30 секунд игрового времени; его позиция остаётся зарезервированной. Возвращение происходит на ней. Вылазка и телепортация недоступны погибшему герою. Сооружения после гибели сами не восстанавливаются.

**RULE-09.** Притянутый с дороги враг получает временную цель/точку движения. Если выжил и контроль закончился, он возвращается к маршруту по заранее допустимому соединению, затем продолжает к трону. Нельзя с помощью крюка создать непроходимую точку, бесконечно незавершаемую волну или телепортировать врага за геометрию карты.

### 2.4. Противники и вылазки

Обычный враг движется по своему маршруту, атакует попавшего в дистанцию блокирующего защитника, затем продолжает движение. Осадная машина выбирает доступное здание по своему приоритету; при отсутствии таких целей движется к трону. Лекарь лечит союзника; диверсант использует боковой маршрут. Приоритеты и tie-break по стабильному ID исключают зависимость от порядка отрисовки.

Отправить героя в вылазку можно только в фазе подготовки. До подтверждения отображаются длительность, награда и отсутствующий в обороне герой. В предлагаемой первой версии исход детерминирован: скрытого шанса провала нет; цена — отсутствие героя на карте. Время вылазки идёт только в боевых тактах, не во время паузы и не по календарным часам. Возвращение автоматическое; при занятых слотах предмет попадает в ограниченный экран выбора награды до следующей волны и не исчезает молча.

Для Рошана награда — одно воскрешение отправленного героя; до использования жетон занимает отдельный явно показанный слот вылазки. Тайная лавка предлагает выбор предмета; лагерь даёт золото. Значения длительности/награды относятся к балансировке. Не создавать отдельную управляемую боевую сцену лесного похода.

### 2.5. Состояния партии

| Состояние | Допустимые действия | Переход |
|---|---|---|
| `loading` | Отмена/повтор загрузки | После полной проверки критических ресурсов → `preparation` или загрузка сохранения |
| `preparation` | Строить, улучшать, продавать, переставлять, отправить в вылазку, начать волну | `start_wave` → `wave` |
| `wave` | Строить, улучшать, применять способности, телепортировать, пауза | Все группы вышли и враждебных единиц нет → `resolution`; HP трона 0 → `defeat` |
| `paused` | Настройки, продолжить, выход с предупреждением о последней контрольной точке | Возвращение в исходную фазу; такты остановлены |
| `resolution` | Показ награды, сбор безопасной контрольной точки | Следующая волна → `preparation`; финальная → `victory` |
| `victory` / `defeat` | Результат, повторная партия, меню | Новая партия получает новый ID |

**Каноническое межволновое состояние.** `resolution` — атомарный переход ядра, а не сохраняемая фаза ожидания. После последнего боевого такта, если трон жив: один раз применить награду волны; удалить оставшиеся снаряды и временные призывы без дополнительных попаданий/наград; завершить оплаченную стройку; завершить активные телепорты выживших героев; остановить незавершённые касты с уже потраченным кулдауном. Затем установить `lastCompletedWave=N`, `nextWave=N+1`, `phase=preparation` и записать контрольную точку. Для финальной волны установить `nextWave=null`, `phase=victory` и сформировать терминальную запись вместо checkpoint. При гибели трона сразу формируется `defeat`, без награды за завершение волны. Показ итогов и затухание эффектов не задерживают этот переход.

Новая партия начинается с `lastCompletedWave=0`, `nextWave=1`. Поле `activeWave` существует только во время боя; одиночного неоднозначного поля `wave` в снимке нет. `start_wave` запускает именно `nextWave`. Загрузка контрольной точки не исполняет `resolution` и не выдаёт награду заново. Награды вылазок, ожидающие выбора, остаются в снимке и блокируют следующую волну до выбора.

| Процесс | Во время `wave` | В подготовке / на паузе / после итога |
|---|---|---|
| Движение, атаки, снаряды, жизнь призывов | Идут по боевым тактам | Боевые такты остановлены; переход `resolution` удаляет временные боевые объекты |
| Кулдауны, воскрешение, длительность вылазки | Уменьшаются по боевым тактам | Остатки заморожены и сохраняются; не сбрасываются между волнами |
| Строительство, телепорт | Идут по боевым тактам | В подготовке действия мгновенные по правилам; остатки завершаются только переходом `resolution` |
| Визуальные частицы и показ награды | Собственные часы отображения | Могут затухать, не меняя игровое состояние |

При скрытии вкладки одиночная игра автоматически ставится на паузу. После возвращения не проигрывать накопившееся календарное время ускоренной симуляцией. Возобновление — явно игроком.

### 2.6. Контракт `game-core`

Предлагается фиксированный такт 30 Гц, отображение независимо от него. Все игровые длительности — целое число тактов; золото/HP/урон — целые значения. Координаты симуляции — целые условные единицы; масштаб преобразования в сцену хранится в конфигурации карты. Визуальная интерполяция не меняет попадания.

Команда: `commandId`, `tick`, `sequence`, `type`, `actorId?`, `payload`. Типы: `build`, `upgrade`, `sell`, `cast`, `teleport`, `equip_item`, `set_priority`, `send_expedition`, `start_wave`, `pause`, `resume`. Адаптер ввода назначает монотонный `sequence` и ближайший допустимый такт; журнал сохраняет назначенные значения. На одном такте порядок команд — `(sequence, commandId)`. Повтор одного `commandId` с тем же телом возвращает прежний результат без повторного действия, с другим телом отклоняется. При возобновлении контрольной точки начинается новая эпоха команд; события и команды брошенной части волны не переигрываются автоматически.

Результат: `accepted` или `rejected` с устойчивым кодом причины. События после принятия: `gold_changed`, `construction_started`, `building_ready`, `cast_started`, `projectile_hit`, `unit_died`, `hero_returned`, `wave_finished`, `throne_damaged`, `run_finished`.

Событие эффекта содержит `eventId`, такт, `effectId`, источник, цели и необходимые координаты. Визуальная система подписывается на события. Повтор показа кадра не повторяет урон или выдачу награды.

Случайность воспроизводима: один закреплённый алгоритм PRNG, seed и его состояние входят в сохранение. Запрещены `Math.random()` и календарное время внутри правил боя. Точный алгоритм и формат состояния закрепляются в версии `game-core` до создания совместимых сохранений.

**Порядок боевого такта:** (1) принять команды и резервы по заданному порядку; (2) уменьшить таймеры, отметить готовые завершения, снять истёкшие состояния контроля; (3) выполнить движение и выбор целей по стабильному ID; (4) сформировать и применить воздействия в порядке `(sourceId, actionSequence, targetId)`; (5) зафиксировать смерти и награды по ID, отменить действия погибших; (6) завершить помеченные стройки, вылазки и телепорты выживших; (7) проверить поражение, затем конец волны. События, созданные стадией, не возвращаются в уже пройденную стадию этого такта. Истёкший контроль снимается до движения; герой, получивший смертельный урон в такт завершения телепорта, погибает на исходной позиции, перенос отменяется. Ранее выпущенный снаряд существует независимо от смерти стрелка; ещё не начатая атака мёртвого источника не создаётся. Правила сортировки, округления и алгоритм PRNG входят в версию ядра.

В подготовке команды исполняются последовательно без увеличения `simTick`; кулдауны не расходуются от ожидания или действий в меню. Пауза/возобновление — управляющие команды адаптера между тактами. До запуска следующей волны фиксируется подготовленный снимок; его локальная запись обязательна, ожидание сети не требуется.

## 3. Бэк

### 3.1. Ответственность и модули

**BE-01.** Один API-сервис. Логические модули: guest-session, content, profile, runs, saves, publisher. Разделение на микросервисы, брокер событий, Redis и постоянно работающий multiplayer-сервер не требуются текущими сценариями.

**BE-02.** Гостевая идентификация: случайный непрозрачный токен в `Secure`, `HttpOnly`, `SameSite` cookie; в БД хранится его хеш. Идентификатор игрока из тела запроса не используется как доказательство доступа. Потеря cookie означает потерю доступа к облачному гостевому профилю; механизм восстановления не обещается.

**BE-03.** Профиль содержит настройки звука/графики/управления и историю своих партий. Публичного доступа к чужим сохранениям нет. API читает/меняет только объекты текущего владельца. Токены, cookie и полный снимок партии не пишутся в журнал ошибок.

**BE-04.** Публикация контента: изменяемый черновик → валидация → неизменяемый release с `contentVersion`, `schemaVersion` формата пакета, `metadataSchemaVersion`, `coreCompatibility`, `assetManifestHash` → атомарное переключение активной версии. Начатая партия продолжает использовать свою версию. Release и сохранение закрепляют точные неизменяемые версии EAV-метаданных по §5.2. Отдельные файлы/версии нельзя смешивать.

Изменение баланса/волн в пределах уже реализованных `behaviorId` публикуется без перезапуска API: каталог версий перечитывается/инвалидируется после фиксации, проекции адресуются по версии и hash. Новый обработчик способности требует релиза кода. Сопоставление `clientReleaseId → coreVersion/contentVersion` неизменяемо; `/bootstrap` учитывает закреплённый клиентский релиз, а не выдаёт старому клиенту неподдерживаемый новый баланс. Активная версия — выбор для нового запуска, не команда заменить данные текущего боя.

`clientReleaseId` обозначает версию набора запуска, а не только байты JS. При обновлении одного контента создаётся новый ID/манифест набора, ссылающийся на прежние файлы фронта и новую contentVersion; прежнее сопоставление сохраняется. Сначала публикуются пакет и новое сопоставление, затем переключается current.json. Launcher передаёт выбранный ID клиенту явно; ID не зашит единственной константой в повторно используемом JS.

**BE-05.** Контент публикуется закрытой CLI-командой/операторским процессом. Публичной административной панели и доступного из игры универсального EAV CRUD нет. Допустимые обработчики поведения ограничены кодом. JSON Schema компилируется только из доверенной конфигурации, не из присланного игроком кода [S09].

### 3.2. Предлагаемый API

Внутри API маршруты имеют префикс `/api/v1`; при предлагаемом размещении рядом с первой игрой публичный путь — `/td/api/v1`, proxy удаляет только префикс `/td`. Данные JSON UTF-8. UUID/ID — непрозрачные строки; даты сервера — UTC ISO 8601. Внутриигровые часы представлены `simTick`, а не датой.

| Метод и путь | Вход | Выход / эффект |
|---|---|---|
| `POST /guest-session` | Без `playerId` | Создать/вернуть гостевую сессию, установить cookie; `profileId` |
| `GET /bootstrap` | `clientReleaseId`, cookie при наличии | Закреплённые совместимые версии ядра/контента, URL манифеста, краткий профиль |
| `GET /version` | — | API releaseId, исходная ревизия, список совместимых клиентских релизов/форматов; без секретов |
| `GET /content/{version}` | Версия | Неизменяемый runtime-пакет, ETag/hash; 404 при неизвестной версии |
| `GET /profile` | Сессия | Настройки и версия профиля |
| `PATCH /profile` | `expectedRevision`, изменённые разрешённые настройки | Новая ревизия; конфликт без перезаписи |
| `POST /runs` | `clientRunId`, `clientReleaseId`, `contentVersion`, `coreVersion`, seed | Созданная партия или прежняя при точном повторе; пара клиент/контент проверена по манифесту |
| `GET /runs` | Курсор | Собственная история и доступные сохранения |
| `GET /runs/{id}` | Сессия | Метаданные своей партии, текущая ревизия, статус |
| `PUT /runs/{id}/checkpoint` | `requestId`, `expectedRevision`, `snapshotSchemaVersion`, `snapshot` | Атомарная запись контрольной точки и новая ревизия |
| `GET /runs/{id}/checkpoint` | Сессия | Последний сохранённый снимок целиком и его ревизия |
| `POST /runs/{id}/finish` | `requestId`, `expectedRevision`, итог victory/defeat и финальный результат | Атомарно: результат, терминальный статус, новая ревизия; безопасный checkpoint не требуется |
| `GET /health` | — | Жив ли процесс; без секретов и конфигурации |
| `GET /ready` | — | Готовность БД и активного контента; 503 при неготовности |

Контракт ошибки: `code`, безопасное `message`, `requestId`, необязательные `fieldErrors`. Базовые ответы: 400 — форма/тип, 401 — сессия отсутствует, 404 — объект не найден или недоступен, 409 — конфликт ревизии/повтора/состояния, 413 — размер, 422 — семантика снимка, 429 — лимит, 503 — временная недоступность.

### 3.3. Сохранения и конкуренция

**BE-06.** Обязательные контрольные точки — перед запуском волны после подготовительных действий и после завершения нефинальной волны. Единственная сохраняемая фаза — каноническая `preparation` из §2.5, где нет активных врагов/снарядов/временных призывов/незавершённого строительства/каналов телепорта. Контрольная точка включает `lastCompletedWave` и `nextWave`, причём награда за завершённую волну уже применена. Перед стартом ядро завершает подготовительные операции; если это невозможно, кнопку старта блокируют с причиной. Финал сохраняется через BE-10, а не как checkpoint в фазе `resolution`/`defeat`.

Для активной волны гарантируется продолжение от последней контрольной точки, а не восстановление каждого кадра. Выход/перезагрузка явно объясняет, какую волну придётся начать заново. Кулдауны, состояние PRNG, вылазки и жетоны сохраняются; пауза сама по себе не создаёт безопасный mid-wave save.

**BE-07.** Каждый checkpoint — атомарная версия всего набора сохранённых сущностей. После проверки владельца и захвата блокировки run сначала проверяется повтор `requestId`: тот же хеш входа возвращает прежний ответ, другой хеш — `IDEMPOTENCY_CONFLICT`. Только после этой проверки сверяются терминальный статус и `expectedRevision`, затем фаза, версия и значения; далее запись и увеличение ревизии. Предварительный поиск операции допустим как ускорение, но не заменяет повторную проверку под блокировкой. Правила одинаковы для checkpoint и finish; точный транзакционный порядок — §5.5.

Две вкладки с одной ревизией не могут обе успешно заменить сохранение. Побеждает первая фиксация; вторая получает 409. Автоматическое слияние золота, предметов и состояния карты запрещено. Локальная копия конфликтующей ветки остаётся доступна для явного решения игрока; по умолчанию облако не перезаписывается.

**BE-08.** При сетевом таймауте повторяется тот же запрос с тем же `requestId`; новая операция с новым ID не создаётся вслепую. Для партии хранить отдельно неизменяемую `pendingOperation` (checkpoint или finish) и `latestLocalCheckpoint` — последнее полное локальное поколение. Пока запрос A не подтверждён, новые безопасные состояния B/C обновляют только локальное поколение, не тело A. После подтверждения A клиент закрепляет полученную ревизию и, если C новее, создаёт новый requestId для C с этой `expectedRevision`; промежуточный B отправлять не требуется. Оба состояния и последняя подтверждённая ревизия атомарно сохраняются в IndexedDB. Одновременно отправляется не более одной операции на партию.

**BE-09.** Проверка сохранения: известные версии и ID, допустимая фаза, уникальные экземпляры, существующие ссылки, совместимость площадок, вместимость предметов, конечные числа и диапазоны из контента, неотрицательная валюта, корректные остатки таймеров. Это защита структуры/целостности, а не античит.

**BE-10.** Завершение партии не требует безопасного снимка: клиент атомарно сохраняет отдельную локальную терминальную запись с итогом, волной, `simTick` и статистикой. Если уже есть неподтверждённая операция, сначала устанавливает её результат; затем отправляет finish с актуальной ревизией. Новейшие ещё не отправленные checkpoint после локального финала не отправляются. Сервер под той же блокировкой и в одной транзакции записывает `run_result`, терминальный статус и новую ревизию вместе с результатом идемпотентной операции. После терминального статуса новые checkpoint/finish отклоняются `RUN_FINISHED`; точный повтор ранее принятого requestId по-прежнему возвращает прежний ответ. Завершённую партию нельзя «Продолжить». Конфликт с другой вкладкой не обходится перезаписью: локальный результат сохраняется для показа, облачная ветка остаётся неизменной. Это не античит и не доказательство честности результата.

### 3.4. Эксплуатационный минимум

- HTTPS, один origin для фронта и API, ограничение методов/размера тела, проверка Origin для изменяющих запросов и параметризованный SQL.
- Предлагаемый предел снимка — 256 КиБ; уточнить по фактическому сохранению. Ошибка размера не удаляет локальную копию.
- Гостевые сессии и ресурсоёмкие операции ограничиваются по частоте; конкретные квоты выбираются по тесту и ожидаемой нагрузке, не объявляются известными заранее.
- Для начала достаточно одного приложения, способного раздавать статический фронт, и PostgreSQL. CDN/объектное хранилище — при необходимости распространения ассетов; не обязательны для первой сборки.
- Обязательное вручную задаваемое подключение — `DATABASE_URL`; порт предоставляется платформой. Параметры окружения должны иметь безопасные значения по умолчанию, где это возможно. Секреты не попадают в клиентский bundle.
- Миграции и seed выполняются контролируемой командой, повтор seed не дублирует сущности. Перед изменениями данных — резервная копия; до выпуска проверить восстановление. RPO/RTO и срок хранения не заданы и требуют отдельного эксплуатационного решения.
- Журналирует `requestId`, код результата, длительность, версию контента и безопасный код ошибки. Нужны счётчики ошибок сохранения, конфликтов, времени загрузки пакета; полный внешний сервис аналитики не обязателен.

### 3.5. Выходы бэка

Исходники API, OpenAPI-контракт, схемы запросов/ответов, модуль сохранений, publisher/validator, примеры ошибок, инструкция запуска с минимальными настройками, контрактные тесты. Отдельно — доказательство конкурентной записи и повтора после потери ответа.

## 4. Фронт

### 4.1. Экраны и управление

**FE-01.** Старт: «Играть», «Продолжить», настройки. Продолжение доступно только после успешной проверки сохранения и соответствующего пакета контента. При отсутствии WebGL2 — понятное сообщение, а не чёрный canvas. WebGPU рассматривается только как опциональный renderer после отдельной проверки.

**FE-02.** Экран боя: карта; сверху волна, золото, здоровье трона, пауза; снизу пять карточек героев, выбранное действие и его состояние. Экран строительства открывается по участку, а не прячется только в общей лавке.

**FE-03.** Квадратные строительные фундаменты отображают пиктограмму здания и состояние доступности. Круглые позиции героев имеют знамя/силуэт. При наведении/выборе — явная подпись «Построить» или «Разместить героя». Изображение одних плюсов без объяснения неприемлемо.

**FE-04.** Цикл строительства: выбор фундамента → три карточки с названием, ролью и ценой → призрачная модель на этом фундаменте + радиус → подтверждение → магическая сборка → активное сооружение. Недостаток золота объяснён текстом; отмена preview не стоит денег. После принятия повторный клик не покупает вторую постройку.

**FE-05.** Выбор героя на карте или клавишами 1–5. `Q` включает прицеливание его основной способности, `Esc` отменяет неотправленное действие/закрывает меню. Кнопка способности показывает цель, готовность, зарядку, кулдаун или сохранённое заклинание. `Space` ставит паузу; остальные hotkey отображаются в подсказках. При фокусе в поле ввода боевые сочетания не срабатывают.

**FE-06.** Прицеливание показывает допустимую область и цели до команды. Неподходящий объект не превращается в случайную соседнюю цель. Ошибочная команда возвращает видимую причину без расхода ресурсов. Показывать ожидаемый эффект улучшения до покупки, включая его цену и новый уровень.

**FE-07.** Телепортация: выбрать героя → кнопку → свободную позицию → подтверждение стоимости/времени → отображение канала. Вылазка: выбрать доступного героя → цель → длительность/награда → подтверждение; карточка отсутствующего героя показывает таймер и недоступность боевых команд.

**FE-08.** Перед волной видны типы противников и направление особой угрозы; запуск явной кнопкой. Начальный tutorial последовательно просит построить, улучшить, применить способность и показывает разницу площадок. Tutorial использует реальные команды, а не отдельную имитацию боя.

### 4.2. Устройство клиента

- `game-core` — независимый пакет TypeScript с чистыми правилами и сериализацией безопасных состояний.
- `renderer` — адаптер состояния и событий в Babylon.js. Удаление графического объекта не означает смерть игрового существа.
- `ui` — HTML/CSS/TypeScript. Тяжёлое состояние симуляции не прогоняется через перерисовку DOM каждый кадр; HUD обновляется по изменениям.
- `content-loader` — проверка версии, манифеста, целостности и нужных ресурсов. Критические модели/данные должны быть готовы до старта волны.
- `save-client` — IndexedDB, очередь одной неподтверждённой операции и API. Проблемы облака не останавливают текущий бой.
- `audio` — включение после пользовательского действия; регулировка музыки, эффектов и общей громкости.

Пути врагов — авторские полилинии/граф с индексом участка и прогрессом по нему. Изменение визуальной модели дороги не меняет навигацию. Способности и призывы используют игровые радиусы/простую геометрию. Полноценная физическая симуляция и runtime-перестроение navmesh для текущих правил не требуются.

### 4.3. Локальное сохранение и сеть

**FE-09.** Перед отправкой контрольная точка атомарно записывается в IndexedDB по BE-08. Для каждого run хранятся последнее локальное поколение, неизменяемая ожидающая операция, подтверждённая серверная ревизия и необязательная терминальная запись. Индикатор различает «Сохранено на устройстве», «Сохранено на сервере», «Не удалось сохранить», «Конфликт». Текст «сохранено на сервере» относится именно к показанному поколению и появляется только после подтверждённой ревизии. Если локальная запись перед стартом волны не удалась, старт блокируется с возможностью повтора; прогресс не объявляется сохранённым.

**FE-10.** При недоступном API уже загруженная партия продолжается. Для первой загрузки нужен доступный пакет контента; полноценная установка PWA/offline-first не заявляется. После восстановления сети выполняется та же идемпотентная операция. Очередь и requestId переживают перезагрузку.

После перезагрузки приоритет имеет локальная терминальная запись: показать результат и восстановить очередь отправки, не предлагать продолжение. Иначе использовать последнее совместимое локальное поколение, включая C при ещё ожидающем A; фоновая синхронизация сначала повторяет точное A. После сверки с сервером конфликт не сливается автоматически. Если локальной копии нет, читать серверный статус и последний checkpoint; терминальный статус исключает продолжение, даже если старый checkpoint ещё хранится. Во время активной волны последнее локальное поколение остаётся её стартовой точкой: текущий бой целиком не сериализуется.

**FE-11.** При загрузке сохранения сверяются `coreVersion`, `contentVersion`, `snapshotSchemaVersion`, `metadataSchemaVersion` и манифест. Несовместимое сохранение не открывается с молча изменённым балансом. Показать причину и сохранить исходную запись. Миграция — отдельный явно поддерживаемый путь с тестом, а не произвольный best effort.

### 4.4. Графическая производительность

Предлагаемые инженерные ориентиры до выбора эталонного ПК: 60 FPS на штатной сцене; проверка 120 врагов, 5 героев, 12 сооружений и нескольких одновременных эффектов; начальная передача до 20 МиБ с отложенной загрузкой необязательного. Эти величины — **кандидаты на бюджет**, не результаты замеров и не аппаратно-независимые обещания.

Для приёмки фиксируются модель CPU/GPU, ОС, браузер/версия, разрешение canvas, профиль графики, версия сборки и сцена. Измеряются frame time p50/p95/p99, просадки, draw calls, число активных частиц, JS heap и время до управления. Без этих входов статус производительности — непроверено.

**FE-12.** Профили качества уменьшают число декоративных частиц, тени и разрешение эффектов, но сохраняют предупреждение, область поражения, видимость цели, момент попадания и различимость площадок. Не допускается «low quality», в котором враг становится невидимым для игрока из-за отключения обязательного индикатора.

Инстансы — для повторяемого статического окружения; отдельные/подходящие анимированные экземпляры — для героев и врагов. Для частиц/снарядов — переиспользование объектов. Измерять прозрачные перекрытия и площадь эффектов, а не только число частиц. Прогрев критических материалов до боя; освобождение ресурсов при повторном запуске партии.

### 4.5. Ветка телефона, если будет выбрана

Устройства и минимальный браузер уточняются отдельно. Предлагаются горизонтальная ориентация, выбор касанием → крупные команды → второе касание цели, отмена отдельной кнопкой, отсутствие hover-зависимых действий. Нужны проверка попадания пальцем по площадкам, safe areas, экранная пауза и отдельная графическая сцена нагрузки. Это дополнительная часть O01; готовность desktop не означает мобильную приёмку.

### 4.6. Выходы фронта

Исходники и сборка клиента, `game-core`, каталог команд/событий, контроллер UI, загрузчик и локальные сохранения, тестовые воспроизведения, профили качества, список ресурсных бюджетов с фактическими замерами. Отдельные демонстрации строительства, крюка, кражи магии и телепортации.

## 5. База данных

### 5.1. Основной принцип

Прикладные данные — типизированная модель **сущность → параметр → значение**. Не создавать доменные таблицы `heroes`, `towers`, `items` со всеми характеристиками в фиксированных колонках. Не складывать всю предметную модель в один JSONB без проверяемой структуры. БД описывает контент и сохранённые объекты; горячая симуляция работает с скомпилированными структурами в памяти.

### 5.2. Таблицы

| Таблица | Минимальные поля и назначение |
|---|---|
| `entity_types` | `id`, `code`, `label`, `schema_revision`, `status`: определения типов, включая ещё не имеющие экземпляров |
| `entity_parameters` | `id`, `entity_type_id`, `code`, `data_type`, `required`, `multiple`, `target_type_id`, `referencePolicy`, `constraints`, `status`: метаданные параметра |
| `entities` | `id`, `entity_type_id`, `owner_id?`, `release_id?`, `revision`, `status`, timestamps: устойчивая идентичность объекта |
| `entity_parameter_values` | `entity_id`, `entity_type_id`, `parameter_id`, `data_type`, `ordinal`, одно из типизированных значений: text/integer/numeric/boolean/timestamp/reference |
| `guest_sessions` | Техническая сессия: хеш токена, профиль, истечение/отзыв; не хранить открытый токен |
| `save_operations` | Техническая идемпотентность: владелец, run, requestId, хеш запроса, зафиксированная ревизия и безопасный ответ |
| `metadata_schema_versions` | Технический неизменяемый манифест точных ID/ревизий типов и параметров, версия и hash; не хранилище прикладных значений |
| `content_releases` | Технический каталог публикаций: версия, metadataSchemaVersion, состояния, хеши, совместимость, активный указатель |
| `runtime_projections` | Пересоздаваемые пакеты контента/снимков: формат, источник, версия, hash; не второй независимый источник истины |
| `schema_migrations` | Выполненные версии миграций |

`constraints` описывает ограниченный язык правил (min/max/enum и т. п.), а не исполняемый JavaScript/SQL. Если требуются составные значения, они моделируются ссылочными сущностями, например `wave_group`, `path_node`, `hero_item_slot`; формат JSON используется на границе API и для производной runtime-проекции.

Определение типа уникально по `(code, schema_revision)`. Сущность ссылается на точный `entity_type_id`; параметр принадлежит именно этой ревизии типа. После использования в опубликованном release или зафиксированном checkpoint эти метаданные неизменяемы. Изменение типа/required/диапазона/множественности/политики ссылок создаёт новую ревизию типа и новые ID его параметров; старые сохраняются. Даже необязательный новый параметр выпускается новой ревизией метаданных без DDL доменной таблицы. `metadataSchemaVersion` закрепляет согласованный набор этих ID; release и checkpoint хранят явную ссылку. Версия структуры снимка, версия метаданных и версия игрового контента — разные значения. Смешанная версия набора при фиксации запрещена; миграция создаёт новое поколение, сохраняя исходное.

### 5.4. Целостность

**DB-01.** У значения обязательны FK на объект и параметр; дополнительно обеспечивается совпадение их типа. Предлагается использовать составные ключи `(id, entity_type_id)` и соответствующие составные FK в значениях. Пара независимых FK сама по себе недостаточна.

**DB-02.** Тип параметра и заполненная колонка значения должны совпадать. Ровно одна колонка значения заполнена. Ноль/false — реальные значения; отсутствие реквизита означает отсутствие строки, не пустую строку и не ноль.

**DB-03.** Для одиночного параметра — единственное значение пары `(entity_id, parameter_id)`; для множественного — уникальный ordinal и явно разрешённая множественность. Способ реализации через ключи/триггер должен проверять также изменение метаданных, не только вставку значения.

**DB-04.** Ссылка указывает на существующий объект допустимого типа и версии. `referencePolicy` параметра явно задаёт допустимую область: тот же владелец, тот же run, то же поколение checkpoint либо закреплённый публичный release. Личная сущность может ссылаться на определение героя из своего закреплённого release, но не на чужое сохранение или saved_hero из другого поколения. Для контента запрещена непредусмотренная ссылка в несовместимую публикацию. Удаление целевого объекта с активными ссылками — RESTRICT; контент архивируется, опубликованная версия неизменяема.

**DB-05.** Обязательность и межобъектные правила проверяются на границе публикации/фиксации полного checkpoint по его закреплённой `metadataSchemaVersion`: отдельный черновой экземпляр допустим без всех значений. Сохранённый/опубликованный набор не допускается с пропуском обязательного реквизита. Изменение required/type/range выпускается новой версией по §5.2; оно не меняет проверку старого сохранения. Старые данные преобразуются только отдельной проверяемой миграцией, а не изменением общих определений на месте.

**DB-06.** Межтабличные условия не прятать в PostgreSQL `CHECK`, читающий другие таблицы: официальная документация не гарантирует такой инвариант [S14]. Использовать составные FK, ограничения уникальности, контролируемые функции записи и необходимые триггеры. API-роль не имеет обходного прямого доступа к таблицам конфигурации.

**DB-07.** Публикация нового набора и переключение активного указателя выполняются атомарно после полной проверки. Читатель закрепляет одну версию. Старые версии сохраняются для незавершённых/доступных сохранений; автоматическое удаление без политики жизненного цикла не включать.

### 5.5. Транзакции и запросы

Контрольная точка записывается как новое поколение объектов. В одной транзакции: проверка владельца → блокировка run → повторная проверка requestId под блокировкой → проверка нетерминального статуса → сравнение revision → запись полного нового поколения → проверка целостности → переключение currentCheckpoint и увеличение ревизии → сохранение результата операции → commit. После фиксации поколение неизменяемо. При сбое до commit старое поколение остаётся активным; при потерянном ответе повтор находит уже записанную операцию. Незавершённое поколение не публикуется.

Для `save_operations` уникален `(owner_id, run_id, request_id)` — одна общая область для checkpoint и finish. Хеш включает вид операции, run ID, expectedRevision, версии форматов и каноническое тело запроса; пробелы/порядок ключей JSON не меняют хеш, транспортные заголовки в него не входят. Канонизация версионируется и проверяется одинаково для первого запроса и повтора. При двух одновременных одинаковых запросах второй после блокировки находит операцию и возвращает тот же ответ до проверки ревизии. При другом теле — 409. Данные идемпотентности сохраняются на весь срок доступности run; произвольная очистка делает обещанный повтор недействительным и не допускается.

Finish использует тот же порядок до сравнения revision, затем записывает единственный `run_result` и терминальный статус вместо поколения checkpoint. Уникальность результата на run и атомарность проверяются отдельно. Поздний новый checkpoint получает `RUN_FINISHED`; точный повтор старой операции возвращает свой исторический ответ, но не изменяет текущий статус. Клиент не выводит статус партии из исторического ответа: терминальность проверяется по `/runs/{id}` и локальной терминальной записи. Все запросы транзакции выполняются одним зарезервированным client [S10].

Основные чтения: контент по release, собственные run по владельцу и времени, последний checkpoint, параметры объекта. Нужны индексы на `(entity_type_id, release_id)`, `(owner_id, entity_type_id)`, `(entity_id, parameter_id)`, `(parameter_id, reference_value)` и уникальность области requestId. Индексы по числовым параметрам добавлять под подтверждённый запрос; не индексировать каждую характеристику заранее.

Компиляция контента читает EAV вне игрового цикла и выдаёт компактный JSON с конкретными полями. В игру загружается именно эта неизменяемая проекция. БД не вызывается для расчёта каждой атаки. Проверка проекции: её hash и sourceRevision должны соответствовать опубликованному набору.

### 5.6. Миграции и выходы БД

Поставка: нумерованные SQL-миграции ядра конструктора, seed метаданных и игрового контента, функции/триггеры целостности, индексы, роли доступа, тестовые данные, пример резервного копирования/восстановления. Повторное применение seed безопасно; несовместимые изменения схемы не выдаются за обычное добавление параметра.

База данных существующих проектов не изменяется этим ТЗ. Целевой сервер — сервер первой игры по U07. Использовать отдельную схему `last_throne` и роль. Наличие PostgreSQL на нём не установлено: изученный пакет развёртывания первой игры R1 прямо описывал поставку без runtime-БД. Если подходящего экземпляра нет, PostgreSQL для этой игры размещается на том же сервере с отдельным постоянным каталогом данных после проверки ресурсов; существующую БД нельзя считать уже подготовленной.

## 6. Графика, эффекты и анимация

### 6.1. Художественная задача

Сохранить компактную low-poly базу, фиксированный высокий ракурс, узнаваемых героев и ясные три дороги. Усилить магию через последовательность и взаимодействие: подготовка → выброс → движение → попадание → затухание. Каждый эффект сообщает действие, источник и область, а не только украшает кадр.

**GR-01.** Старый экран — ориентир ракурса/палитры. Круглые плюсы заменяются на два типа мест из FE-03. В новом контрольном кадре должны одновременно быть видны: свободный квадратный фундамент, построенное здание, призрачный preview другого здания, герой на круге и временный призыв. Нельзя показать все пять категорий одной одинаковой платформой.

**GR-02.** Простые модели и переиспользуемые материалы сохраняются. Выразительность достигается формой, ритмом и локальным светом. Полноэкранный bloom, постоянный дым над дорогами и одинаковые цветные шары для всех способностей неприемлемы.

### 6.2. Реестр графической поставки

| Группа | Минимальный состав предлагаемой базовой партии | Особенности |
|---|---|---|
| Герои | 5 моделей, 5 портретов, 5 основных иконок + 3 состояния украденных заклинаний | Поиск силуэта/цвета каждого героя; точные модели не заменять случайным готовым бойцом |
| Враги | 6 моделей ролей; 3 командира, допускающие общее базовое тело с отличимыми деталями | Различение роли без чтения имени |
| Здания | 3 семейства × 3 читаемых уровня | Уровни могут использовать модульные детали; отдельные состояния стройки/разрушения |
| Призывы | Надгробие, зомби, змеиный тотем | Согласованные точки появления и исчезновения |
| База | Трон, разрушенные бараки, остатки башни, баррикады, курьер | Трон — единственный главный световой акцент вне кастов |
| Карта | Дороги, земля, деревья, камни, стены, 2 типа площадок, лагеря | Повторяемые модули; точное соответствие навигации |
| UI | Рамки/состояния карточек, золото, HP, кнопки действий, статусы, прицелы | Текст отрисовывается интерфейсом, не запекается в PNG |
| Эффекты | Крюк, кража, 3 украденных каста, надгробие/зомби, змеи, выстрел, 3 атаки зданий, стройка, телепорт, смерть/попадание | Версионированные presets и текстуры |

Количество размещённых площадок — часть данных карты: предлагаются 12 строительных участков и 8 тактических позиций для 5 героев. Проверить плотность на контрольном кадре; это ещё не утверждённая карта.

### 6.3. Контракт моделей

Основной runtime-формат — `.glb`; редактируемый исходник — `.blend` там, где модель создана/доработана в Blender. Единый масштаб, pivot у основания, согласованное направление вперёд, без отрицательного масштаба. Экспортёр и runtime закрепляются версиями; ориентация проверяется после импорта.

Клипы персонажей: `idle`, `attack`, `cast`, `hit`, `death`, `teleport`; `walk` — для перемещающихся врагов/призывов. Неприменимый клип явно отмечается в manifest, не угадывается по имени. Зацикливание, длительность и события попадания задаются метаданными. Событие урона исходит из ядра; клип подстраивается под его тайминг.

Сокеты по применимости: `projectile_origin`, `spell_origin`, `hook_origin`, `hit_center`, `selection_origin`. Bounds и игровая коллизия описываются отдельно от сложной поверхности модели.

Предлагаемые стартовые бюджеты: герой 2–5 тыс. треугольников, рядовой враг 0,5–1,5 тыс., здание 1–3 тыс.; по возможности 1–2 материала на объект. Это ориентиры поставщику, корректируемые после измерения сцены. Нельзя принять модель только по количеству полигонов: число материалов, прозрачность, скелеты и текстуры также измеряются.

Текстуры объединяются по семействам, базовая палитра используется повторно. Сначала проверить обычный GLB; сжатие включать после подтверждения загрузчика и декодера. Внешний CDN декодеров не должен быть единственным условием запуска игры.

### 6.4. Постановка магии

Указанные времена — предлагаемые визуальные ориентиры; фактический момент игрового эффекта принадлежит `game-core`.

| Событие | Последовательность | Доступный способ реализации | Что должно остаться на низком качестве |
|---|---|---|---|
| Кража Rubick | Подсветка чужого заклинания → отделение фрагментов → дуга к посоху → заряд на нём | Частицы по траектории, emissive-материал, короткая линия | Источник, направление переноса, значок сохранённого заклинания |

| Надгробие Undying | Зелёный круг → светящиеся трещины → подъём надгробия → руки/зомби | Плоская маска, несколько мешей, анимация подъёма | Область и реальные активные призывы |
| Змеи Shaman | Круг с рунами → последовательное появление → синхронный первый залп | Маска круга, scale/translation, короткие дуги снарядов | Число и позиции змей, попадания |
| Магическая башня | Разгон вращающихся колец → заряд ядра → разветвлённая молния → затухание | Простые кольца-меши, линии, небольшая вспышка | Реальные поражённые цели и цепочка |
| Постройка | Световой план → подъём блоков → фиксация кристалла → короткая волна завершения | Анимация частей модели, preview-материал, круг | Фаза стройки, занятость участка, момент готовности |

| Выстрел Sniper | Прицел → короткий след → отчётливый удар | Line/trail и hit sprite | Выбранная цель и попадание |

Предлагаемый ритм ключевого каста: читаемая подготовка 0,2–0,4 с, выразительный пик 0,3–0,8 с, быстрое затухание. Эти интервалы не добавляются поверх игрового кулдауна произвольно; после согласования они переводятся в длительности эффектов и клипов.

**GR-03.** Ограничивать одновременно активные декоративные слои и динамические источники света. Деградация сначала убирает вторичные искры/дым, затем снижает плотность и разрешение; игровой след и телеграф остаются. Сила магии проверяется на движущейся сцене, а не только на красивом скриншоте.

### 6.5. Графический конвейер

1. Серый blockout карты и два типа мест; проверить выбор мышью и читаемость.
2. Один эталонный герой, одна магическая башня и один противник; установить масштаб и палитру.
3. Эталонный эффект кражи Rubick и магической сборки здания в реальном движке.
4. Проверить эффект в записи и интерактивно: начало, пик, затухание, перекрытие дорог и HUD; выполнить протокол первого запуска из §7.1.
5. После принятия эталона — остальные модели, эффекты и UI по тем же правилам.
6. Оптимизация GLB, атласы, локальные presets; импорт/проверка в игре.

У каждого ассета: `assetId`, назначение, source, author, license, sourceFile, exportFile, hash, scale, clips, sockets, dependencyIds. Imagegen-картинка не отмечается как готовая модель или анимация.

### 6.6. Права и совместимость материалов

Наборы Kenney/KayKit из исследования относятся к окружению и техническим заготовкам, а не дают права на персонажей Dota. Доступность исходных моделей в Steam/Workshop сама по себе не считается разрешением встроить их в самостоятельную браузерную игру. Условия Valve различают обычное использование, developer tools и fan art [S16]; применимость к этому выпуску ещё не установлена. До распространения требуется отдельное решение по материалам и правам, без молчаливой смены выбранного мира.

| A25 | §6.3–6.5 | Импортировать каждый поставленный GLB; сверить клипы, sockets, scale, текстуры и сохранность после оптимизации |

Для A02/A21 нужна фактическая проба с человеком: собственное впечатление автора или согласие проверяющего агента не доказывает понятность и эмоциональный эффект. Для приёмки анимаций прикладывается запись и доступная сборка; статичный макет недостаточен.

### 7.1. Протокол понятности строительства и магии

Предлагаемый порог для согласования в P1: пять человек из целевой аудитории, ранее не видевших сборку; минимум четыре из пяти проходят каждый пункт. Это небольшая практическая проверка интерфейса, не статистическое исследование. До набора участников закрепить состав, задания, порог и эталонную версию; до выполнения протокола A02/A21 имеют статус «не проверено».

1. На первом запуске, без пояснений разработчика и без tutorial, участник за 60 секунд самостоятельно выбирает квадратный фундамент и подтверждает постройку; затем показывает место для героя и отличает временный призыв. Штатные подписи и подсказки самой игры разрешены. Ошибка выбора круглой позиции как фундамента фиксируется; подсказка модератора означает непрохождение попытки.
2. Для четырёх коротких сцен — кража Rubick, призыв Undying, стройка и телепорт — участник своими словами называет источник, цель/область и результат. Названия героев помнить необязательно. Для кражи должен отличить получение способности от нанесения урона; для телепорта — исходную и целевую позиции.
3. Повторить проверку ключевой информации в обычном и низком качестве, чередуя порядок профилей между участниками. Сохраняются доступная сборка, записи попыток, ответы и ошибки. Эталонные записи фиксируются после принятия; последующая графика сравнивается с ними. Успешный tutorial отдельно проверяется по FE-08 и не подменяет первый самостоятельный запуск.

## 8. Порядок реализации, игровые релизы и обновление

R0 — отдельно согласованная техническая поставка. P0–P6 — внутренние этапы игровой работы. R1–R4 — самостоятельные игровые поставки. Выпуск R1 не объявляется выполнением всей спецификации полной партии.

| P0: фиксация решений | O01–O04, контрольная техника, версии инструментов | Только после этого документ можно объявить утверждённым заданием на зависимую реализацию |
| P1: техническая проба | Один маршрут, герой, башня, враг, строительный preview, насыщенный эффект; краткие постановочные сцены остальных ключевых эффектов | Согласовать и выполнить §7.1, закрепить эталон магии до массового производства моделей |
| P2: ядро партии | Три линии, волны, золото, урон, строительство, способности на временных моделях | A03–A12; правила независимы от графики |
| P3: БД и API | Контент, гостевой профиль, поколения сохранений, восстановление | A14–A20, A27; EAV-инварианты и реальные транзакционные тесты |

Готовность передачи разработчику: утверждённые правила/объём, словарь, схемы команд/состояний, API и save-контракт, каталог метаданных, реестр ассетов и критерии A01–A27. Точные численные боевые настройки хранятся в версионированном наборе контента, а не дублируются в коде/UI.

### 8.2. Размещение на сервере первой игры

**Подтверждено:** U07 задаёт тот же сервер. Изучен сохранённый `FoxyGame-R1-Desktop-Handoff.zip` от 3 октября: для первой игры он описывает VPS Timeweb, Docker frontend/backend, host Nginx → loopback `8080`, собственный `/api/` и отсутствие БД в R1. Это исторический пакет инструкций, не readback нынешнего сервера. Пользователь позднее сообщал о размещении первой игры по адресу `https://129.101.114.184/`; актуальность маршрутов/портов/контейнеров в этом задании не проверялась.

**Предлагаемое размещение:** первая игра сохраняет свой существующий путь и сервисы; «Последний трон» получает `/td/` на том же HTTPS-origin, API `/td/api/v1`, отдельный runtime-контейнер приложения, собственные каталоги и роль/схему БД. Не требуется отдельный оплачиваемый сервер или домен. Правило `/td/` в host Nginx имеет приоритет над существующим общим маршрутом первой игры; `/api/` первой игры не перенаправляется в новый API. Наличие валидного HTTPS-origin устанавливается перед исполнением; не обходить проверку TLS.

Предлагаемые пути на хосте: `/opt/last-throne/releases/<releaseId>/` для неизменяемых сборок, `/opt/last-throne/state/` для указателей/журнала доставки; постоянный каталог PostgreSQL отдельно. Это новые пути проекта, не описание уже существующих. Порты A/B назначаются после проверки занятости, доступ только через host Nginx/loopback; наружу не публикуются. Cookie `last_throne_guest` имеет `Path=/td`, HttpOnly/Secure/SameSite; IndexedDB использует собственное имя БД. Общего аккаунта/профиля с первой игрой текущий scope не предполагает.

Перед установкой снять факты: фактические контейнеры/Compose, bind mounts, Nginx-конфигурация, CPU/RAM/диск, место под предыдущий и новый релизы, наличие PostgreSQL, пределы соединений, канал команд. В R1 handoff нет доказанной свободной БД или запаса памяти. Совместное размещение принимается только после проверки запаса на первую игру + PostgreSQL + одновременно A/B этой игры. Сборка выполняется вне VPS; на нём размещается готовый артефакт. Увеличение тарифа и новые платные услуги не выполняются этим ТЗ.

Задать лимиты памяти/CPU контейнера, размер/ротацию журналов, предел пула PostgreSQL и таймаут блокировок миграции по измеренным ресурсам. Схемы/роли не изолируют RAM, диск и серверные блокировки. При недостающем запасе остановить продвижение новой версии; не выключать первую игру ради освобождения ресурсов. Численные лимиты выбираются после обследования, не выдаются за известные.

### 8.3. Обновление без пересоздания runtime-контейнера

Под «без перезапуска образа» зафиксировано обычное обновление без `docker restart`/пересоздания контейнера приложения. Образ среды содержит закреплённые Node.js, supervisor и системные зависимости; код и ассеты находятся в постоянных каталогах хоста, подключённых целой директорией через read-only bind mount [S17]. Загрузка новой версии меняет файлы вне образа. Новый API-процесс запускается, старый завершается; неизменность PID API не обещается. Первичная настройка mount/supervisor выполняется один раз в R0 до R1. В реализации R0 стабильный Node gateway внутри runtime один раз подключается к host Nginx для `/td/`; обычные обновления переключают A/B внутри gateway и не перезагружают общий Nginx. Смена Node.js, ОС образа или системных/native-зависимостей вне совместимости закреплённой среды — отдельное обслуживание с заменой контейнера; не объявлять его обычным обновлением без рестарта.

| Что меняется | Механизм | Что происходит с работающей партией |
|---|---|---|
| Фронт, JS игрового ядра, GLB, текстуры, эффекты | Новый каталог релиза; атомарное переключение `current.json` после проверки | Текущая партия использует прежнюю закреплённую сборку; новая выбирается в меню/при новом запуске |
| Баланс/волны/параметры известных обработчиков | Новая contentVersion и новый манифест набора запуска с новым clientReleaseId; прежние файлы JS можно использовать повторно; затем current.json | Старый run остаётся на прежнем contentVersion; API и контейнер не перезапускаются |
| Код API и совместимые JS-зависимости | Запустить неактивный A/B процесс, проверить, переключить upstream, дренировать прежний | Локальный бой продолжается; сохранения принимаются по совместимому контракту |
| Метаданные/структура БД | Совместимое расширение и проверяемая миграция, затем promotion кода | Старые определения/снимки сохранены; перезапуск PostgreSQL не нужен для обычного DDL, но возможные блокировки контролируются |
| Node/native/system runtime | Отдельная поставка runtime-образа | Требует отдельного плана обслуживания; гарантия отсутствия рестарта не распространяется |

**DEPLOY-01 — идентичность.** Один проверенный артефакт включает `releaseId`, SHA исходников, hash фронта/бэка/графики, core/content/metadata/snapshot версии, совместимость API/схемы БД и режим отката. Каталог нельзя изменять после публикации. JS-зависимости поставляются отдельно для каждого релиза по lockfile; не запускать `npm install` в активном каталоге и не менять общий node_modules работающей версии. Не делать `git pull` в production как замену проверенному артефакту.

**DEPLOY-02 — клиент.** Небольшой стабильный launcher `/td/` читает `/td/current.json` с `Cache-Control: no-store`. Указатель содержит releaseId, URL манифеста и точные core/content версии. Файлы лежат под `/td/releases/<releaseId>/`, имеют неизменяемые адреса/hash и могут кэшироваться как immutable. Vite собирается с согласованным base для этого пути; URL моделей/контента не вычисляются из изменяемого `current` [S18]. Launcher не регистрирует service worker, автоматически подменяющий файлы активного боя. Указатель заменяется атомарным rename на той же файловой системе после наличия всего пакета; директорий/ссылок вне mount нет. Новая версия показывается в меню; автоматическая перезагрузка посреди боя запрещена.

Продолжение старого run выбирает именно совместимый архивный клиентский релиз и его манифест. До принятия политики срока поддержки старые файлы/контент, необходимые доступным сохранениям и открытым партиям, автоматически не удаляются. Сброс браузерного кэша не является штатной командой обновления. Сам launcher изменяется отдельной обратно совместимой поставкой; закрытый старый launcher тоже должен уметь выбрать новый манифест.

**DEPLOY-03 — бэк.** Supervisor в постоянном runtime-контейнере запускает выбранный API из каталога релиза и восстанавливает его после падения/пересоздания контейнера по сохранённому состоянию. На время выпуска работают A и B с разными портами и DB-пулами. Deployment-команда имеет эксклюзивную блокировку для этой игры и постоянный журнал фаз/версий; после обрыва сначала сверяет реальное состояние и продолжает, не запускает второй switch вслепую. Записанный выбор API/клиента (`selection.json`), журнал (`journal.json`) и `current.json` сохраняются вне контейнера. Закрытая операторская CLI использует Unix socket mode 0600; TCP/public deploy API отсутствует.

Порядок продвижения:

1. Загрузить и проверить полный неизменяемый артефакт, фактическую совместимость runtime/память/диск, старый релиз для восстановления. Только после этого начать изменения БД.
2. Выполнить совместимые expand-миграции контролируемой ролью с таймаутом блокировок. Сбой оставляет старый API рабочим; необратимый contract в этот выпуск не включается.
3. Запустить B без публичного продвижения; проверить `/ready`, `/version`, версии контента и отдельно сценарии старого checkpoint, нового checkpoint, точного повтора requestId и finish на тестовом run.
4. При первой установке проверить полный host Nginx (`nginx -t`) и выполнить один graceful reload, добавив только `/td/` к loopback gateway. В обычном обновлении атомарно закрепить намерение API, переключить внутренний маршрут gateway на B и проверить ревизию через `/td/api/v1/version`. Общий Nginx не перезагружается; его соединения первой игры не участвуют в дренировании. Gateway больше не назначает A новых запросов и отдельно считает запросы, уже направленные A.
5. Только после успеха публичной проверки API атомарно переключить `current.json` на новый клиент. Между шагами API обязан обслуживать старый и новый клиент. Общей транзакции файлового указателя и маршрутизации не предполагается.
6. Проверить прекращение направления новых запросов именно к A и число его активных HTTP-запросов/транзакций; соединения первой игры не входят в этот критерий. Только после доказанного прекращения маршрутизации закрыть приём A, завершить запросы и DB-пул, остановить только A. Timeout drain применяется к A, не к общим workers; при обрыве запроса клиент повторяет тот же requestId. Если прекращение маршрутизации к A не удалось установить, оставить A рабочим и отметить вывод старого процесса незавершённым: не освобождать его порт/каталог для следующей поставки и не объявлять gate пройденным. Node предоставляет закрытие HTTP-сервера без приёма новых соединений [S20]. Успех проверяется состоянием процессов и запросами, не только exit code команды.
7. Зафиксировать активные фронт/API версии, результаты smoke и состояние первой игры. Ни глобальный Compose down, ни очистка Docker/каталогов первой игры в update/rollback не входят.

API новой версии поддерживает формы запросов, snapshotSchemaVersion и metadataSchemaVersion всех клиентских релизов, чьи партии/сохранения доступны. Старый клиент по-прежнему вызывает API после вывода A: одного pin ассетов недостаточно. Если новый API несовместим, этот механизм switch неприменим — сохранять старую версионную маршрутизацию или блокировать promotion до реализации совместимости. Совместимость проверяется матрицей клиента/сохранения/API, а не только номером `/api/v1`.

**DEPLOY-04 — откат и данные.** У релиза заранее закрепляется проверенный режим: `pair` — прежний API принимает уже записанные новой версией данные, можно вернуть upstream и client pointer; `frontend_only` — вернуть новый запуск на прежний фронт, оставив совместимый новый API; либо исправление вперёд, если возврат невозможен. Release с непроверенным восстановлением не продвигается. Возврат pointer не меняет код уже открытых вкладок; прежний API при pair обязан поддерживать и такие вкладки. Восстановление резервной копии не выполняется автоматически: оно может удалить новые записи других пользователей. Contract/удаление старых определений разрешены только после вывода поддержки старых клиентов **и** сохранений, а не после остановки процесса A.

Поставка deployment: одна закрытая операторская команда обновления по releaseId и одна команда восстановления по разрешённому режиму; проверка hash/версий/readiness, взаимное исключение, журнал, smoke/readback включены внутрь. Никакого публичного `/deploy` и исполнения присланного из игры кода. Инструмент/канал доставки выбирается по фактическому серверному доступу; наличие работающего CI или SSH сейчас не заявляется.

### 8.4. Критерии обновления и совместного размещения

Эти проверки дополняют A01–A27. Они проводятся на стенде, затем в согласованном охвате на целевом сервере; настоящие обновление/откат в этом задании не исполнялись.

| ID | Различающий сценарий | Ожидаемый результат и свидетельство |
|---|---|---|
| DEP-01 | Начать старую партию, обновить только фронт/эффекты/баланс | Текущая партия и сохранение используют прежние версии; новый запуск выбирает новый манифест; никаких Docker restart/recreate |

### 10.4. R3 — контракт текущей реализации

Поручение U11, contract_revision r3/1, docs/R3-CONTRACT.md. Продолжает уже выбранный стек и базовые решения: PC solo, guest, local deterministic battle, cloud checkpoints. R4/аккаунты/телефон не добавлены.

R3 содержит15волн, пять героев, три здания, шесть обычных ролей и командиров5/10/15 (осада/обход/магическое усиление). Диверсант использует отдельный маршрут и скрыт без действующего детектора; лекарь лечит союзников, бронированный враг имеет снижение урона. Новый content —151типизированная EAV-сущность.

Вылазки начинаются только в preparation: лагерь300тактов/160золота, лавка600тактов/выбор одного предмета, Рошан900тактов/один привязанный Aegis. Одновременно отсутствует один герой; anchor зарезервирован, атака/каст/телепорт недоступны. Таймеры идут только в боевых тактах. Предмет лавки остаётся pending reward до явного выбора/замены либо подтверждённого отказа; start_wave заблокирован. Aegis имеет отдельный слот, автоматически потребляется при следующей гибели своего героя и восстанавливает полный maxHP в той же стадии разрешения смерти.

Два слота предметов: split_charm — дополнительная цель, swift_charm —25% сокращения периода атаки, sight_gem — обнаружение в радиусе700, healing_lantern —8HP/90тактов в радиусе280. Уникальность по behavior; bounds/compatibility/цены из content. Команды send_expedition/equip_item/choose_reward/discard_reward проверяются до мутации; замена всегда явная, награда не исчезает при заполненных слотах. Числа — стартовый баланс, не подтверждение удовольствия.

Pins r3-core-1/r3-content-1/r3-meta-1/save4/API1. Save4 хранит два item slots, expedition с оставшимися боевыми тактами, bound token и pendingRewards. SQL007/008 аддитивны; старые001–006 неизменны. Объекты/ссылки/ordinal дочерних записей хранятся scalar typed EAV; opaque JSON-снимок не является источником истины. Сервер проверяет закреплённый runtime/save tuple и hash R3 projection; старые runs обслуживаются своим runtime-парсером. R1/R2 продолжаются exact архивными клиентами с прежними5/10волнами, без неявной конверсии.

Фронт содержит подтверждение вылазки с длительностью/наградой/отсутствием героя, два слота/предпросмотр/замену предмета, ограниченный экран pending reward и отдельный Aegis. Новые процедурные props, эффекты departure/return/reveal/healing/resurrection/finalboss и звук дополняют существующие круглые hero anchors, квадратные фундаменты и насыщенную магию. Звук включается действием пользователя, учитывает mute/pause; low/contextloss/возврат проверяются в доступном браузере.

R2 runtime принимает R3 точным client ID; r3-* wildcard в старом verifier не поддержан. Будущий content-only client ID объявляется заранее в API manifest (поставка предусматривает r3-content-002). Обычный R2→R3 — candidate migration/grants вне watched parent, immutable install, A/B API→client switch, без пересоздания runtime/Nginx. Frontend-only rollback оставляет R3 API/save4; pair rollback кR2 запрещён. Для cold-recovery до commit есть документированная граница: видимый непродвинутый R3 при selectionR2 паркуется только после readback selection/journal/current/live status, затем recover.
