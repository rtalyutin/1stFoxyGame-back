# R0 — техническое основание «Последнего трона»

Пользователь подтвердил технический R0 4 октября 2026. Цель — подготовить отдельную браузерную игру к размещению на VPS первой игры. Игровые механики начинаются с R1. R0 не создаёт бой, гостевые профили или облачные сохранения и не закрепляет открытые продуктовые решения O01–O06.

## Состав

- TypeScript/Vite: технический экран, загрузка, реальные ответы API, ошибка/повтор; версия вкладки закреплена URL релиза. HTML launcher получает `current.json` без кеширования.
- Node 24/Fastify: `health`, `ready`, `version`, `bootstrap`, `content` под `/td/api/v1/`. Подтверждённый EAV-контент читается из PostgreSQL, секреты остаются на сервере.
- PostgreSQL: отдельная БД и схема `last_throne`, типизированный EAV, неизменяемые опубликованные метаданные и контент, миграции с транзакцией, блокировкой и контрольной суммой.
- Поставка: воспроизводимая npm-сборка с lockfile, неизменяемый каталог каждого релиза, SHA256 всех файлов, проверка совместимости и раздельные версии клиента/API/ядра/контента/метаданных/API/сохранений.
- Runtime: постоянный Node-шлюз, API A/B внутри одного контейнера, journal и атомарные указатели. Команды оператора используют локальный канал; публичного deploy API нет.

## Уточнение §8.3 ТЗ

Вместо перезагрузки общего host Nginx при каждой поставке используется постоянный шлюз TD. Host Nginx один раз направляет `/td/` на `127.0.0.1:8091`. Шлюз внутри контейнера переключает A/B и считает запросы к каждому процессу. Это сохраняет первую игру и позволяет доказать завершение запросов старого TD-процесса, не ожидая остановки чужих Nginx workers. Обновления кода/контента не пересоздают контейнер; изменение Node, ОС или самого шлюза требует отдельного инфраструктурного выпуска.

## Приёмка R0

1. Launcher открывает текущий immutable URL. Старая открытая вкладка сохраняет свой ID и контент при обновлении API.
2. Реальный API отвечает только совместимому клиенту; отсутствие БД/контента делает readiness отрицательным. Ошибки не раскрывают connection string.
3. SQL отвергает неверный тип значения, чужой параметр, недопустимую ссылку/кратность, неполную публикацию, изменение опубликованных данных. Повтор миграций безопасен, изменённая checksum отклоняется.
4. A/B обновление сохраняет запросы в полёте, проверяет hashes/readiness/compatibility до promotion, восстанавливается после прерывания и допускает совместимый rollback.
5. Первой игре не меняются её контейнеры, маршруты, cookie, volumes, базы или репозитории. Исчерпание ресурсов проверяется на фактическом VPS до включения.

## Границы проверки

Локально доступны Node, браузер и встроенный PostgreSQL через PGlite. Docker, Nginx и подключение к VPS здесь отсутствуют. Тесты SQL в PostgreSQL/WASM и реальных Node-процессов подтверждают локальные свойства. Не заявляются фактическое размещение на VPS, сохранение container ID, нагрузочная пригодность сервера или отсутствие 502 в его сети. Эти проверки описаны в runbook и остаются обязательными для первой установки.

Будущие API сохранений R1 должны выполнить ограничения idempotency/checkpoint/finish из основного ТЗ; R0 не подтверждает сохранение боёв. Wildcard совместимости разрешён только для технических `r0-core-*`, `r0-content-*`, `r0-meta-*`; он не разрешает неизвестные игровые форматы.
