# Целевая БД R2: типизированный конструктор

Статус B02: спроектировано для PostgreSQL 18. Это не выполненная миграция; R1 не подключается к БД. Базовая схема конструктора, миграции, контрольные триггеры и PostgreSQL-интеграционные тесты создаются в R2 (B05). Авторизация, профиль и экономика подключаются в R3.

Прикладные сущности хранятся через метаданные, не через фиксированные таблицы `players(gold,...)` и не одним JSON-документом. Четыре таблицы ядра:

| Таблица | Поля и назначение |
| --- | --- |
| `entity_types` | `id UUID PK`, `code UNIQUE`, `archived_at`; явный каталог типов, включая типы без объектов/параметров |
| `entities` | `id UUID PK`, `entity_type_id FK`, `revision BIGINT >=0`, `state` (`draft`, `active`, `archived`), timestamps; устойчивый объект даже без значений |
| `entity_parameters` | `id UUID PK`, `entity_type_id FK`, `code`, `label`, `data_type`, `is_required`, `is_multiple`, `is_unique`, `reference_type_id FK`, диапазоны/ограничения, `archived_at`; `UNIQUE(entity_type_id,code)` |
| `entity_parameter_values` | `entity_id`, `parameter_id`, `entity_type_id`, проверяемые копии `data_type`, `is_multiple`, `is_unique`, `position`, типизированное значение, `reference_type_id`; `PK(entity_id,parameter_id,position)` |

Типы значений: `text`, `integer`, `decimal`, `boolean`, `timestamp`, `reference`. Физические nullable-колонки: `value_text TEXT`, `value_integer BIGINT`, `value_decimal NUMERIC`, `value_boolean BOOLEAN`, `value_timestamp TIMESTAMPTZ`, `value_reference UUID`. CHECK требует ровно одну непустую колонку и её соответствие `data_type`; `num_nonnulls(...) = 1` недостаточно без проверки соответствия. JSON используется только там, где сам реквизит действительно является документом; для текущих доменных реквизитов такого типа не требуется.

## Обеспечение целостности

1. `entities UNIQUE(id,entity_type_id)`. Значения ссылаются составным FK `(entity_id,entity_type_id)` на него.
2. `entity_parameters UNIQUE(id,entity_type_id,data_type,is_multiple,is_unique)`. Значения ссылаются тем же составным FK на метаданные. Чужой тип параметра, неправильный тип значения и подмена флагов не проходят независимо от клиентской формы.
3. Для reference обязательны `value_reference` и `reference_type_id`. Составной FK `(value_reference,reference_type_id)` ведёт на `entities(id,entity_type_id)`, а `(parameter_id,reference_type_id)` — на `entity_parameters(id,reference_type_id)` с соответствующим UNIQUE. Для нереференсного типа обе reference-колонки NULL. Это проверяет существование и разрешённый тип цели.
4. `position >= 0`; для одиночного параметра CHECK `position=0` и частичный `UNIQUE(entity_id,parameter_id) WHERE NOT is_multiple`. Множественность не кодируется JSON-массивом.
5. Бизнес-уникальность включается только для нужного реквизита. Отдельные частичные UNIQUE-индексы `(parameter_id,value_text)`, `(parameter_id,value_integer)` и аналогично для остальных типов при `is_unique=true` предотвращают конкурентный дубль. Регистр/нормализация уникального login задаётся метаданными и единой функцией сохранения до записи, не произвольным lower() только на клиенте.
6. Отсутствие обязательного реквизита невозможно проверить CHECK одной строки значения. Deferred constraint triggers на `entities`, `entity_parameter_values` и существенных изменениях `entity_parameters` проверяют полноту `active`-объекта перед commit. Триггеры блокируют затронутый объект перед проверкой; изменение метаданных блокирует тип и объекты в устойчивом порядке, проверяет все существующие данные. Draft допускает незаполненность, активный игровой профиль — нет.
7. Диапазоны и ограничение количества элементов задаются типизированными метаданными; транзакционный сохранитель/триггер блокирует entity и проверяет их. Обычный межтабличный CHECK для этого не применяется. Удаление последнего обязательного значения, уменьшение max count и изменение типа метаданных должны проверяться так же, как INSERT.
8. Тип и параметры с живыми значениями не удаляются: `ON DELETE RESTRICT`, архивирование запрещает новые записи и сохраняет старые. Смена типа/множественности/диапазона реквизита — отдельная совместимая миграция с проверкой и, при необходимости, преобразованием значений. `ON UPDATE CASCADE` не переинтерпретирует уже записанные типы.
9. Ссылки на аккаунт/каталог по умолчанию `ON DELETE RESTRICT`; удаление аккаунта не выполняет неявный cascade инвентаря. Жизненный цикл и архивирование задаёт сервер. Права менять конфигурацию есть только у обслуживающей миграции, игровая роль не меняет таблицы метаданных.

Составные FK, CHECK и UNIQUE выполняет сама PostgreSQL. Прикладной пользователь БД не должен обходить сохранитель/триггеры прямой записью. Будущая реализация покажет SQL и проверит эти свойства на настоящем PostgreSQL, а не только mock.

## Начальные типы и операции

| Тип | Примеры параметров |
| --- | --- |
| account | login, enabled |
| profile | account reference, gold integer, last-production-at timestamp |
| inventory-entry | profile reference, catalog-item reference, quantity integer, upgrade-level integer |
| equipped-slot | profile reference, hero reference, slot-code text, inventory-entry reference |
| building | profile reference, building-kind reference, level integer |
| hero / ability / catalog-item / recipe | код и конфигурация по метаданным; рецепты с typed ссылками на ингредиенты |

R2 создаёт и проверяет ядро конструктора; R3 добавляет только реально нужные типы/параметры аккаунта, профиля и экономики. Buildings появляются вместе с кликером R5. Новый необязательный параметр — запись метаданных без DDL новой доменной колонки. Gold — целое, не floating point; HTTP ограничивает представление безопасным целым JavaScript. Цена/награда вычисляется по версии каталога на сервере.

Технические `credentials`, `sessions`, `applied_migrations`, `operations`, `economic_ledger` и `run_validation_log` допустимы отдельно: это учёт доступа/выполнения, а не обход прикладного конструктора. Они ссылаются на entity ID. `operations UNIQUE(account_id,operation_id)` защищает повтор; журнал изменений и значения профиля фиксируются одной транзакцией. Возможные проекции балансов и владельцев производные, не второй источник истины. Сервер проверяет владение до чтения и записи; фильтрация готового ответа не является защитой.

Индексы помимо PK/FK: `(entity_type_id,state)` для объектов нужного типа; `(entity_id,parameter_id)` для профиля; `(parameter_id,value_reference)` для ссылок и принадлежности; typed индексы только под реальные запросы каталога/логина. Каждый индекс ускоряет конкретный запрос ценой дополнительных записей; неизмеренные проекции не добавляются заранее.

## Приёмка миграции R2

Обязательные различающие сценарии R2: объект без необязательных значений; новый параметр без изменения domain DDL; неизвестный объект/параметр; чужой тип параметра; неверная типизированная колонка; дубликат одиночного реквизита; несуществующая/чужого типа ссылка; отсутствующее обязательное значение при публикации; удаление последнего обязательного значения; несовместимое изменение метаданных; конкурентная запись уникального параметра; backup/restore и повтор миграции. На R1 они подготовлены как критерии, не исполнены.

В R3 к ним добавляются проверки прикладных аккаунтов и экономики: одновременные записи уникального login, конкурентное списание золота, атомарное завершение забега и повтор операции.

Основание модели: согласованная схема проекта «БД как конструктор» и [PostgreSQL 18 constraints](https://www.postgresql.org/docs/18/ddl-constraints.html). Межтабличные гарантии не приписываются обычному CHECK.
