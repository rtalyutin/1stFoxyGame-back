# Backend R2: B05–B07

Контракт: утверждённый план R2, GDD и ACTIVE_CONTRACT парной front-ревизии. Во frontend остаётся непрерывный client-authoritative бой. Backend не включает награды или неаутентифицированные операции от имени переданного клиентом accountId.

## Типизированный каталог

Каждый враг/оружие и сам снимок каталога — entity конструктора. Связь врага с оружием — typed reference, список врагов/оружия и углы залпа — явные multiple values с position. Правила и физические величины — integer/decimal, не JSON-тело внутри сущности. Есть определения пустых типов `account`/`profile`, без аккаунтов, значений или операций R3.

Версии `catalogVersion`/`rulesVersion` сейчас `r2.1`. Definition ID включает версию каталога; каждая definition имеет обязательную typed reference на свой снимок. Один код врага/оружия может иметь отдельные definitions в разных версиях без перезаписи старой. Catalog version уникален. PostgreSQL fixture создаёт следующий снимок с изменённой скоростью того же `boss` и сверяет обе версии. Новая миграция использует `contentSeedSql(nextCatalog,false)` после проверки нового источника, сохраняя общие определения параметров.

Обычный и сильный враг требуют ровно одного попадания, босс не меньше трёх. Валидатор не принимает неизвестный weapon reference, modifier или лишнее поле. GET возвращает прямой проверенный JSON-снимок без кеширования. В R2 JSON и его typed seed составляют одну проверяемую версию выпуска; HTTP не читает произвольный изменяемый каталог из БД. CI и migration CLI проверяют совпадение источника и SQL. Новая версия каталога должна вводиться новой согласованной миграцией; уже применённая `002` не переписывается.

Начальный баланс: телеграф стрелка 0.8 сек., интервал 3 сек.; телеграф босса 1 сек., интервал 3.5 сек., три пули под -15/0/+15°. Скорость пули 8 м/с; максимум один живой босс. После смерти источника пули продолжают лететь. Это настройки R2, не финальный баланс.

## Миграции и восстановление

`db:migrate` запускает `dist/db/migrate-cli.js` с PostgreSQL major 18. Ровно один источник соединения: `DATABASE_URL` либо `DATABASE_URL_FILE`. HTTP-контейнер не получает это значение. Runner удерживает session advisory lock, сверяет SHA256/prefix всех ранее применённых файлов, выполняет каждый новый файл и запись `applied_migrations` одной транзакцией. Ошибка SQL/constraint откатывает файл; успешно применённые предыдущие файлы остаются. Журнал технический, вне четырёх прикладных таблиц.

Перед изменением уже используемой БД оператор снимает pg_dump с метаданными, значениями, ограничениями и журналом; сохраняет предыдущую пару приложения. Восстановление проверяется pg_restore на отдельной БД с readback каталога/числа значений и повторным migration runner. Для R2 нет destructive down. Нельзя откатывать только SQL-файл или удалять checksum, чтобы повторить несовместимую миграцию: нужен restore проверенного backup либо совместимая следующая миграция. Prod backup/restore — отдельное действие выпуска, локальные fixtures не подтверждают его выполнение.

## Внутренний RunLedger

`createRun(accountId)` вызывается доверенным кодом и связывает UUID runId, случайный uint32 seed и версии каталога/правил с owner. R2 не разрешает браузеру объявлять владельца: HTTP start/events/finish маршрутов ещё нет. Сервис в памяти процесса; restart теряет журнал. Это рабочая и проверенная внутренняя реализация контрактного слоя B07, без durable экономического commit.

Генератор регистрирует врагов через `registerEnemy(owner,runId,code,spawnTick)` и получает ID `runId:enemy:sequence`; неизвестный/чужой ID отклоняется. Пакет содержит UUID batchId, версии и 1–128 событий с UUID eventId, целым tick 60 Гц и непрерывным sequence. События cast/hit/end имеют закрытую схему; поля наград/accountId запрещены. Повтор того же batchId/payload возвращает результат; другой payload даёт конфликт. EventId также дедуплицируется по каноническому хэшу. Failed batch не оставляет частичных hit/cast/terminal изменений.

Числовой castId внутри backend — порядковый номер 1,2,3… в пределах server runId. Frontend R2 использует строку `clientRunId:cast:sequence`. Они пока не передаются между процессами. При интеграции R3 адаптер строит `serverRunId:cast:castId`, не принимает произвольную строку чужого забега и сохраняет один номер на повтор одного нажатия. Enemy ID также будет сопоставлен с серверным забегом до включения rewards. Текущий клиентский random seed не объявляется серверным.

Один cast может задеть только одну цель и один раз. Три разных cast нужны для босса; повтор hit не уменьшает здоровье. Сервис проверяет минимальную перезарядку, существование cast/enemy и монотонные ticks. Это проверка протокола, не доказательство геометрической достижимости, hitbox, возврата хука или честности клиента. Эти проверки, authenticated owner и воспроизводимый server seed обязательны в R3 до начисления денег.

Terminal end единственный. Новый batch/враг после него запрещён; точный retry принятого terminal batch безопасен. Контакт/прорыв требуют живого врага; hero_hit разрешён от стрелявшего врага даже после его убийства, поскольку выпущенная пуля сохраняется. Никакого API или метода начисления наград в R2 нет.

## Авторские проверки этой подготовки

`npm test`: 15 проверок HTTP/OpenAPI/catalog/RunLedger прошли; `npm run typecheck`, `npm run validate:content` прошли. PostgreSQL fixtures подготовлены к обязательному CI gate на настоящей PostgreSQL 18, включая pg_dump/pg_restore. Локальный запуск БД не состоялся: среда предоставляет только uid0 без права смены пользователя, а PostgreSQL запрещает запуск от root. Это не PASS SQL-интеграции. Результат CI и независимой QA фиксируется отдельно для опубликованного SHA.
